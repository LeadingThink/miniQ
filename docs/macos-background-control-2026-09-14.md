# macOS 后台应用控制：邮件任务对比与实现

## 查到的差别

本次对照本机已安装 ChatGPT 的 macOS 控制接口、用户指定的已完成邮件任务，以及 miniQ 对应会话的工具记录。没有再次发送邮件，没有复制 ChatGPT 的私有实现或依赖其私有辅助进程。

ChatGPT 的邮件任务使用 `cua` 的应用定向接口：按网易邮箱大师的 bundle ID 获取应用，读取该应用的 AX 控件与窗口截图，按元素 ID 点击按钮、直接设置主题和文件选择器路径，也使用应用定向按键和文字输入。它没有用内置网页浏览器代替网易邮箱大师。完成记录还检查了已发送邮件与附件。

本机 JavaScript 包装层把每次动作连同目标应用传给原生 IPC 辅助进程。能据此确认其应用定向 API 与本次任务实际使用的方法；包装层并不公开辅助进程的所有 OS 实现细节，不能据此声称读到了完整闭源实现。

miniQ 此前的 `computer_use` 使用 Enigo 的全局鼠标/键盘输入。截图和输入绑定当时的前台窗口；用户切换窗口后，为避免输入到错误应用，工具会拒绝继续。实际记录中包含多次 `foreground window changed during capture`、`display layout or foreground window changed`，以及一次小写 `space` 不被识别。独占租约只防多个 miniQ 任务互抢，不能避免与用户争用光标。

真机验收还定位到窗口查询的性能放大：底层截图库的 PID、标题、应用名和几何 getter 各自重新查询全部窗口，逐窗读取会形成重复全量扫描；每页观察又存在重复验证。本轮应用控制改用公开 Quartz API 一次读取窗口元数据，并减少同一观察调用中的重复校验，保留输入前的进程身份、窗口几何和 AX 归属检查。

这不是两款产品的统一速度测试：ChatGPT 任务约 8.5 分钟，也有收件人与文件选择器的纠正过程；miniQ 会话还包含前面的 PPT 工作，不能直接比较整个会话的工具数量或耗时。

官方说明也区分 macOS 与 Windows：macOS 支持用户在另一应用继续工作时执行后台任务；Windows 的当前桌面控制会占用前台和指针。本次改进实现 macOS 路径，不宣称 Windows 也有相同后台隔离能力。

来源：[OpenAI Computer use](https://learn.chatgpt.com/codex/computer-use)。官方文档用于核实平台和权限边界，具体 miniQ 改动依据实际代码和本机验收。

## 新实现

`app_automation` 是原生应用控制路径，`browser_automation` 继续负责网页，`computer_use` 明确负责需要接管前台的场景。

| 环节 | miniQ 的行为 |
| --- | --- |
| 发现 | 按 PID、进程启动身份、窗口 ID 识别目标。窗口列表冻结后分页，切换前台应用不会使后续页面漏项。不可访问的系统窗口明确标记，不阻断普通应用发现。 |
| 观察 | 保留目标窗口的 AX 引用，分页展开控件，不截断文字。保留 AXChildren，并合并文件浏览器的公开 AXColumns 和滚动区的 AXContents，去重并标明来源。实测文件面板的列会出现 AXChildren 为空而 AXContents 有内容的情况，补全后才能读到文件行及屏外列。辅助功能已授权时，纯 AX 操作不依赖屏幕录制权限。 |
| 填写与点击 | `setValue` 用文字、数值或布尔值写可编辑控件，检查类型及控件公布的数值上下限；支持替换文字选区。`invoke` 只执行该控件实际公布的 AX 动作，例如按钮的 AXPress。拒绝会主动接管前台的 AXRaise。无需移动用户指针或借用公共剪贴板。 |
| 附件 | 使用控件实际公布的滚动、打开与选择能力进入目录、选择文件，再执行确认按钮。支持原生文件选择器内由系统视图服务提供的控件，通过真实 AX 父链验证归属。 |
| 定向输入 | 对支持的控件投递进程定向键盘、点击和滚动；核对目标应用的 key window，绝不默默改为全局输入。 |
| 视觉 | 可选仅截取目标窗口。图片通过既有模型视觉附件和分块 RPC 展示，工具文字输出不塞 base64。 |
| 防误操作 | 输入消耗观察 ID；验证窗口、进程启动身份、几何和元素归属。窗口关闭、引用过期、不可编辑或受保护控件均拒绝操作。 |
| 恢复 | 输入已投递但后续观察失败时，保留 `actionDispatched` 和具体观察错误，要求核对结果，不因截图失败重复点击。系统面板等 AX 动作单独等待至 10 秒，普通属性读取仍为 2 秒；超时结果不确定时先观察，不盲目重放。投递成功不等于任务成功。 |
| 多任务 | 同一目标应用独占，不同应用可并行持有控制；前台桌面接管与全部后台控制互斥。取消和超时释放租约。 |
| 权限 | 查看和控制分别授权，范围含进程启动身份与窗口；修改文档标题不会反复丢失授权，进程重启不能继承旧范围。 |
| 对话 | 原生任务优先应用定向操作。用户已明确授权的发送操作不重复询问；密码、认证挑战等仍需用户处理。 |
| 展示 | 过程显示后台应用操作及目标应用/窗口，截图标注应用观察，与全桌面观察区分。 |

同时修复前台工具的命名按键大小写问题，例如 `Space`、`space` 和 `SPACE` 均能识别。

## 验收与范围

可重复的真实 Cocoa 验收入口见 [应用控制验收](testing/app-automation.md)。测试创建独立的目标应用和前台干扰应用，只操作临时文本、计数按钮和临时附件，不连接真实邮箱。

自动回归覆盖：观察 ID 和跨任务/窗口隔离、进程授权身份、窗口及控件分页、权限不足零输入、跨工具实例锁、取消释放、操作后观察失败不重放、截图与模型图片附件、前端应用状态和截图、只读计划模式、RPC 会话隔离。

真实应用仍有差异：部分自绘控件不提供 AX 支持，部分应用不接受后台事件；用户同时修改同一个目标应用也可能冲突。应用自身可能在打开模态窗口时激活窗口，此类行为需要实际验收，不能仅凭使用 PID 事件就承诺所有应用无感。未用真实邮件发送作为重复测试，也不宣称通用任务成功率已与 ChatGPT 相同。

本机 AppKit 文件面板的实测还表明：后台快捷键可以到达正确进程和窗口，却不触发“前往文件夹”。因此实测附件流程使用 AX 选择目录、选择文件，再操作确认按钮。`key` 的投递结果始终要求后续状态核对，不把投递次数当成功次数。

截至 2026-09-14，工具与权限相关回归、前端全部 659 项测试及发布脚本 41 项测试通过；前端生产构建和工作区、Tauri 编译检查通过。最终清除诊断代码后的真实 Cocoa 验收四项全部通过，串行运行 11.76 秒：中文字段、多行正文和按钮计数；完整原生附件选择及正确文件名读回；非空目标截图及模型视觉附件；自绘控件的分批 Unicode 输入、组合键、真实坐标点击和双轴滚动。每项均检查前台应用、全局光标和真正的键盘修饰键没有变化。这些合成场景不衡量真实邮箱发送速度或通用任务成功率。

第四项验收定位并修复了单看“已投递”无法发现的问题：仅设置 CG 指针下窗口字段不能让 AppKit 事件获得窗口编号；跨进程构造还需要消除主屏坐标翻转，保留目标窗口内的位置。生产代码现在使用公开 NSEvent 构造接口绑定窗口，并完成一处明确的坐标转换，同时用于点击和滚动。没有私有事件字段、全局输入替代、激活目标应用或测试事件转发。原生回归覆盖窗口编号、窗口坐标、独立事件源、目标进程和滚动数据；真机验收另核对实际控件收到的事件与效果。

发行版本与签名安装包通过现有 GitHub Actions 发布流程生成；上述源码和合成验收不能替代发布产物校验。

# 临时图片附件失效导致会话无法继续

## 根因

用户从微信临时目录附加图片时，旧入口只把文件的绝对路径存入消息，没有把原始图片字节保存到 miniQ 管理的数据目录。微信清理临时文件后，这个路径失效。

视觉历史会保留最近一批用户参考图；即便后续只发送文字，或者历史经过压缩，这一批图片仍可能进入下一次请求。三个模型协议的序列化器都会在 HTTP 发送前读取图片，因此一个失效路径会反复触发 `cannot read attached image`。换模型和重试无法重建已删除的文件。

本次本机核查中，相关失败发生于模型调用开始后的 0–2 毫秒。在同一会话的既有 `view_image` 记录中找到了对应路径的未缩放快照，并核对 PNG 格式、119×124 尺寸和 35,860 字节大小。将这一确切副本恢复到缺失路径后，文件比较和图片读取通过。未删除会话、修改实时数据库、重启应用或自动执行用户的任务。

恢复后再次只读检查日志：两次新的模型调用均已完成，会话回到空闲状态。

## 改动

- 接受图片附件时，在持久数据目录保存原始字节；消息记录只在保存成功后引用它。覆盖直接发送、运行中的排队消息和改写消息。
- 保留原文件名、MIME 类型和全部字节，不通过缩略图或 OCR 替换原图。使用受限文件权限和既有的有界、安全文件读取。
- 新发送的缺失附件仍被明确拒绝；未持久化消息对应的新快照会清理，已提交附件和用户原文件保持不变。
- 真正构建模型请求时，如果读取或编码图片失败，从本次请求的附件字段中移除该文件，再立即重新构建请求。失效、权限不足、超过限制及无法解码的图片均走这条统一路径，不把它们变成整个会话的失败，也不空耗网络重试。
- 只移除出错的精确路径，保留正文和其他有效图片；不删除原消息或归档。模型收到简短的 `unavailable_attachment` 说明，不能猜测未看到的图片，只有任务确实依赖它时才要求补充。图片恢复后下一轮重新可读。
- 重构只处理结构化的本地附件错误，每轮必须实际减少附件字段，因此不能无限循环。HTTP、鉴权和其他模型错误仍按原逻辑处理。单独的发送前文件存在性扫描已移除，避免检查通过后文件才消失的竞态。
- 远程文件读取允许本会话已存储或已排队附件的精确路径，不开放附件目录及相邻文件，不向其他会话授予读取权限。

## 验证范围

- 持久保存后删除临时来源，原始字节仍可读取；改写和排队消息使用相同机制。
- 旧历史中缺失图片与有效图片混合时，继续文字任务、归档读取、压缩和恢复均保留证据信息。
- 使用回环 HTTP 服务验证真实 Responses、Chat Completions 和 Anthropic Messages 序列化。在有工具及无工具模式下，故障附件被移除后仅发送一次 HTTP 请求；恢复后下一轮重新包含图片。覆盖缺失、无权限、目录、过大和解码失败，以及压缩恢复、工具调用对和无正文图片消息。
- 远程附件读取检查会话隔离、排队附件、相邻文件、目录和符号链接边界。

这些测试不调用收费模型。源代码修复需要随新版客户端安装才会生效；恢复当前缺失文件是现有安装版本可立即使用的局部修复。

持久化及远程访问的既有验证：图片附件入口、模型图片安全处理、队列集成各 9 项通过；文件 RPC 6 项及存储附件相关 4 项通过。请求重构的新增验证随本次代码一并执行。

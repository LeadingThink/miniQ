# miniQ 0.1.76 产品与技术改进报告

日期：2026-10-01

## 结论

miniQ 的能力面已经超过一个普通聊天客户端，具备会话队列、审批、目标、子任务、技能、插件、远程主机、手机中继、CLI、文件工作台、定时任务、记忆和 IDE 接入等基础。但当前产品的问题集中在“能力之间缺少统一的可理解状态”：用户能启动很多事情，却不能始终快速判断现在发生了什么、为什么停下、下一步该做什么，以及这个动作会改变什么。

0.1.76 应把产品主线从“功能集合”收束为一个连续的工作空间：输入任务，看到清晰的权限边界，观察进度和产物，在失败处获得可恢复的动作，在技能和连接器中找到可复用能力，再从桌面、CLI、手机和 IDE 继续同一项工作。

## 苹果式产品原则

苹果的可借鉴之处不是颜色或圆角，而是把人的注意力、信任和控制感放在系统中心：

1. **先让人理解，再让人操作。** 每个状态有明确的人话标题、原因和下一步；系统错误不能直接成为用户界面文案。
2. **直接操控，结果可预测。** 卡片、文件、目标和队列都应该能从当前上下文继续操作；危险动作显示影响范围并允许撤销。
3. **渐进披露。** 默认界面只显示当前决策需要的信息，详情、日志、权限和原始错误在需要时展开。
4. **连续性。** 会话、草稿、目标、文件上下文和审批状态跨窗口、CLI、手机、IDE 保持一致；切换上下文时旧响应不能污染新上下文。
5. **反馈必须连续。** 加载、空状态、执行中、等待审批、失败、成功和已取消都必须有稳定视觉状态；不能出现白屏或“完成但其实失败”。
6. **默认值替人做低风险决定，高风险动作要求明确同意。** 沙箱、工作区、网络、远程主机和外部服务用同一套权限语言表达。
7. **无障碍与触控是基础质量。** 所有图标按钮有名称，键盘焦点可见，移动端不用悬停才能完成任务，减少动态效果时仍保留状态信息。
8. **克制。** 借鉴 WorkBuddy 的技能入口、连接器分组、权限解释和定时任务字段；不复制积分推广、空白页面和把失败标成完成的交互。

## WorkBuddy 实测结论

已登录实测确认：它的技能、连接器和定时任务入口容易找到；权限菜单用一句话解释“默认沙箱，超出范围再询问”，并提供完全访问开关；定时任务表单覆盖名称、提示词、频率、有效期和外部同步；快捷入口先向输入框添加标签而不是直接发送；执行成功后会展示产物和验证结果。

同时确认了三处不应复制的问题：401 会显示原始 `401 Unauthorized`，但任务仍标记为“已完成”；失败任务没有重新登录或重试；项目页可出现没有加载或空状态的白页。miniQ 的目标是用更清楚的状态模型和可恢复动作解决这三个问题。

## 当前差距与优先级

### P0：状态、失败和恢复

- 统一定义会话状态：queued、running、waiting_approval、waiting_user、paused、succeeded、failed、cancelled；状态栏、侧栏、通知、CLI 和移动端使用同一映射。
- 把 provider 401/403、网络中断、权限拒绝、工具失败和用户取消转换成用户可理解的标题、原因、影响和动作；原始错误只放在“查看技术详情”。
- 失败必须提供“重试本回合”“重新配置模型/登录”“复制错误详情”；重试使用原 prompt、附件和工作区快照，不能重复发送已经成功的副作用工具。
- 所有异步页面有 loading、empty、error、retry 状态，尤其是项目、技能、连接器和定时任务。

验收：模拟 401、超时、审批拒绝和工具失败；每种状态均显示正确的人话文案，重试不会创建重复会话，当前会话切换后旧响应不会覆盖新会话。

### P0：工作区与权限

- Composer 附近显示当前工作区、沙箱权限和模型；权限入口使用“默认沙箱 / 需要时询问 / 完全访问”三段式解释。
- 审批、等待回答和失败进入同一个待处理中心；数字只计算需要用户动作的事项，未读单独显示。
- 记录权限决定、来源设备、影响范围和撤回动作；远程端提升权限必须二次确认并通知主机。

验收：桌面、手机、CLI 对同一个审批看到相同状态；拒绝后任务可继续或安全结束；权限变化有审计记录。

### P1：技能与连接器成为可理解的能力库

- 技能列表支持搜索、来源、启用状态、依赖缺失、版本和工作区范围；详情页先显示“能做什么、何时会使用、需要什么权限”，再显示 SKILL.md 原文。
- 导入、更新、删除都提供结果反馈和撤销窗口；签名、来源、版本和冲突状态可见。
- 连接器按“已连接 / 可连接 / 需要重新授权 / 不可用”分组，显示权限范围、最后同步时间和断开入口。
- 工具按需加载，默认只显示与当前任务相关的技能和连接器，避免把数量当作体验。

验收：空列表有下一步；请求失败有重试；缺少依赖能一键打开安装说明；启用状态跨重启保留；远程项目导入不误写本地。

### P1：会话、文件和长任务连续性

- 目标、计划、队列和回合按 sessionId 单一归属，组件不再维护容易过期的重复副本。
- 长会话按回合虚拟化，保留底部锚定、生成中滚动保护和阅读位置；文件工作台的树、预览、终端和浏览器入口使用相同工作区上下文。
- 支持从当前回合分支新聊天、临时聊天、重新生成多个版本、新窗口和复制 Markdown/路径；这些动作明确显示是否复制上下文。
- 真实项目下验证大目录、长文件名、超大文件、WebKit、Windows/Linux 和 SSH。

验收：100+ 回合滚动不明显卡顿；切换会话、窗口和设备不串目标、不丢草稿、不重复工具副作用。

### P1：定时任务与预算

- 定时任务显示下一次执行、上次结果、失败原因、暂停/恢复、有效期和时区；失败可以重试或跳过，不把错误写成成功。
- tokenBudget、时间预算和回合限制从协议字段贯通到实际执行、状态卡、CLI 和移动端；结束时说明是完成、预算耗尽还是被用户取消。
- 记忆写回以结构化事件记录成功、失败和跳过，支持同一线程续写与显式清除。

### P2：运行环境、CLI、IDE、移动端与发布

- daemon 启动时生成受控工具环境快照，继承用户登录 shell 的 PATH、cargo、node 和包管理器路径；子任务继承同一快照并在缺失时给出安装提示。
- CLI 补齐审批卡、问题卡命令识别、vim 模式、自定义快捷键、配置局部更新和安全的 `--full-auto` 命名；与桌面共享同一事件协议。
- VS Code 扩展完成安装、启动 daemon、项目关联、会话恢复、认证失败和 Remote SSH 的真实闭环。
- iOS 先完成 inspect/prepare/submit/release 的真实凭据验证，再做 TestFlight 小范围验收；桌面发布先草稿、安装冒烟、再切换更新清单。

## 实施顺序

1. 合并最新 `origin/main`，保留现有 WorkBuddy 技能页、iOS 自动化、VS Code 扩展和 0.1.75 改动。
2. 实现统一状态文案与错误恢复协议，补齐会话失败卡、项目/技能/连接器/定时任务的 loading、empty、error 状态。
3. 收敛待处理中心和权限说明，补充跨端事件与回归测试。
4. 完善技能详情、依赖、导入撤销和连接器状态，再做真实工作区验收。
5. 实现长会话性能与会话连续性缺口，完成 CLI、IDE、移动端验证。
6. 运行前端、Rust、CLI、移动端、发布清单和安装包检查；提交、推送、构建 Release、同步下载页，核对版本、链接、大小和 sha256。

## 发布门槛

- 代码：工作树无未解释改动，格式、类型、单元、集成和端到端关键测试通过。
- 产品：成功、失败、等待、空白、权限和重试路径都有截图或自动化证据。
- 安全：密钥不进入日志和预览；远程权限升级有二次确认和审计；插件环境变量按白名单传递。
- 发布：GitHub Release、OSS latest/manifest、下载页生产清单和实际安装包版本一致；至少一个 macOS、Windows 或 Linux 安装包完成启动冒烟后才切换自动更新地址。

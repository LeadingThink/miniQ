# 本地后台无响应与 Git 查询资源控制

## 2026-10-30：0.1.190 后台失去响应

现象：使用中断开本地连接，重新打开桌面端后出现「本地后台服务在 90 秒内未就绪」。旧 daemon 仍存活，桌面端会继续等待该进程，重开窗口不能恢复。

现场证据：

- 旧 daemon CPU 持续超过一个核心，HTTP `/health` 在 3 秒内没有响应。
- 进程采样显示多个 Tokio worker 正在 `gateway::git::diff_stats` 中创建 Git 子进程。
- 保存的进程快照中有 5,658 个管道句柄和 2,325 个僵尸子进程。
- 两个实际工作区分别有约 4,600、17,500 条 Git 状态记录；`git status` 本身约 100 毫秒完成，后续逐文件统计放大了工作量。
- 停止失去响应的旧进程后，桌面端启动新 daemon，HTTP 健康检查及本机连接恢复。

根因：未跟踪文件通过每个文件一个 `git diff --no-index` 统计行数。旧并发限制仅适用于单个请求，多次界面刷新可以叠加多个请求；客户端取消查询、超时或断开本地连接后，服务端仍保留计算。Git 子进程没有统一超时和完整取消回收，持续创建进程最终拖垮运行时。远程 relay 日志中的连接失败不是此次本地故障的根因。

## 修复后的边界

- 所有 Git gateway 命令共享 4 个执行槽位。单条命令的 30 秒截止时间包含排队时间。
- 未跟踪文件使用临时 intent-to-add index 和临时 object directory，批量添加路径后一次计算 `--numstat`。不修改用户真实暂存区，也不向真实 object directory 写入对象。
- 路径使用 NUL 分隔，保留特殊文件名；支持从仓库子目录发起查询以及 sparse checkout 范围外的未跟踪文件。
- 取消或超时先停止 Git 进程树，再等待直接子进程退出，最后释放执行槽位和临时目录。
- 本地客户端对 `git.status`、`git.diff`、`git.branches` 的取消使用 JSON-RPC 通知：

  ```json
  {"jsonrpc":"2.0","method":"request.cancel","params":{"requestId":"req_1"}}
  ```

- 这些只读查询属于发起它们的 WebSocket，断开连接即清理。通知不能取消模型任务或写操作。Git 查询超时也不会关闭整个客户端连接。
- 本地启动等待已耗尽时，首次失败即显示原因并继续重连，不再隐藏到第三轮失败。

超大文件的 Git 统计仍可能触发单条命令超时；该请求会失败并清理进程，后台与其他任务继续服务。不会以截断文件列表或伪造行数来完成统计。

## 验证

回归覆盖批量结果、真实暂存区与对象目录隔离、未出生分支、文本与二进制、Git attributes、符号链接、特殊路径、子目录和 sparse checkout；还覆盖全局并发、排队超时、执行超时、取消后子孙进程清理，以及真实 WebSocket 断开后模型任务继续完成。

1,500 个文件的 8 次并发查询同时执行 HTTP 健康检查。另在实际工作区的隔离 daemon 中验证：17,536 条记录完整返回；含大文件的另一工作区触发受控超时。并发验证期间的 311 次 HTTP 健康检查全部成功。

## 恢复操作

先保存 daemon 日志、进程采样和资源快照，检查是否有正在运行的任务。服务还能响应时，优先使用认证 RPC `daemon.shutdownIfIdle`：它会原子检查任务、请求及消息队列，繁忙时拒绝退出。需要中断任务时应先取得用户的明确选择，再使用 `daemon.shutdown`。

仅当服务已无响应、无法通过 RPC 恢复时，核实 `daemon.json` 对应的实际进程再定向停止。不要删除数据库、会话记录或所有 miniQ 数据，也不要仅因 PID 存活就认定后台健康。

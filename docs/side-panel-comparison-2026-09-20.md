# miniQ 与本机 ChatGPT：侧边面板比较与改进

核查日期：2026-09-20。miniQ 基于本地 `codex/mobile-chat-actions` 工作区；本机 ChatGPT 为 26.901.51231（8109），bundle `com.openai.codex`。

## 结论

主要差距是工作连续性：ChatGPT 把不同内容组织在统一工作台中，用户可以一边看文件、网页和修改，一边把具体位置带回对话。miniQ 已有多格式预览、浏览器多标签、会话隔离和宽度调整，但入口分散，切换后找回内容、定位修改对象的流程不完整。

本轮补齐统一工作面板、计划和产物概览、文件标签管理、选区提问、审阅导航和左栏筛选。不宣称已经实现 ChatGPT 的全部侧板能力：原生终端、跨面板拖动、Office 精确批注、浏览器区域批注等仍存在差距。

## 证据与边界

- 读取本机 `/Applications/ChatGPT.app/Contents/Resources/app.asar` 对应前端资源；抽查五个主资源的 SHA-256 与已有解包内容一致。下面的实现能力来自代码核查，不等于所有账号、平台或功能开关都开放。
- 原生 UI 工具拒绝访问 `com.openai.codex`，因此没有声称直接操作 ChatGPT 界面完成对照实验。miniQ 的运行验收使用生产 React 组件构成的本地预览和自动化测试。
- 已实际读取官方 [文件预览](https://learn.chatgpt.com/docs/artifacts-viewer?surface=app)、[内置浏览器](https://developers.openai.com/codex/browser)、[集成终端](https://developers.openai.com/codex/integrated-terminal)、[功能索引](https://developers.openai.com/codex/app/features)。
- 仅学习功能结构和交互原则，miniQ 改动按现有组件、RPC 和状态模型独立实现。

## 性能原则

1. 工作面板只复用已加载计划和产物，不额外拉取完整会话，不扩大 relay 数据量。
2. 浏览器页面有稳定 ID，切换文件/审阅只暂停可见视图，不销毁正在填表的浏览器实例。
3. 文件大载荷仍在隐藏时释放；恢复时按现有读取链路重新读取，保留的是轻量视图数据。没有声称所有文件切换都“零请求”。
4. 重复点击当前类别不会触发关闭再读取。
5. 目录在用户展开时才请求；保持服务端分页，不递归遍历全项目。
6. 不用不同功能的冷启动时间作速度比较；本轮没有可比的两客户端端到端延迟实验，因此不报告“快几倍”。

原生 WebView、真实 Office 文件的复杂版式、iPhone/Android 真机和远端网络波动不由浏览器 fixture 代替。当前运行的 miniQ 未重启，版本号未修改，本轮未发布安装包。

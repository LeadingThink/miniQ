## 适用场景

- 改动写完，准备提交、开 PR 或交给用户审阅前，做一轮结构化自检
- 计划里有多个彼此独立的步骤，例如分别修改互不相关的模块、批量处理多个文件或数据源，可以并行加速

## 前置条件

- 项目在 git 仓库中，自检需要 `git diff`
- 并行分派需要 `agent_run` 可用

## 步骤

### A. 评审前自检

1. **看完整 diff**（`shell_run`）：
   - 执行 `git status` 和 `git diff`（已暂存的改动加 `--staged`）
   - 逐文件阅读，而不是只看自己记得改过的地方
2. **按清单检查**，对每一项记录"通过"或具体问题：
   - 需求：是否满足 `sp-clarify-plan` 中确认的验收标准，有没有多做或漏做
   - 正确性：边界值、空值、错误路径、并发与重入、资源释放
   - 测试：新行为是否有测试，是否运行过完整测试套件（`shell_run`）
   - 安全：
     - 是否有硬编码密钥，可以用 `grep -nE "(api[_-]?key|secret|token|password)\s*[:=]"` 检查
     - 注入风险：SQL、命令、路径
     - 权限检查
   - 可维护性：命名、重复代码、残留的调试日志 / `TODO` / 注释掉的代码
   - 兼容性：公共 API、配置项、数据迁移是否向后兼容
3. **跑机器检查**（`shell_run`）：lint、类型检查、格式化，例如 `npm run lint && npx tsc --noEmit`、`ruff check && mypy`、`cargo clippy -- -D warnings`
4. **修复并再过一遍**（`file_edit`），然后输出一份简短的自检报告，列出改了什么、怎么验证的、剩余风险。

### B. 并行分派子任务

5. **判断能否并行**：只有同时满足以下条件的子任务才适合并行：
   - 输入明确
   - 不写同一个文件
   - 不依赖彼此的结果
   - 不操作同一个浏览器页面或应用
   否则按顺序执行。
6. **写清任务书**：给每个子任务写明以下内容，所有子任务使用统一的质量标准：
   - 目标
   - 精确的输入路径或 ID
   - 允许修改的文件或目录范围
   - 验收标准和要运行的验证命令
   - 输出格式和单独的输出文件
7. **启动**（`agent_run`，`runInBackground: true`）：
   - 一批 2–4 个，先全部启动，再在本地做其他独立工作
   - 需要隔离的代码改动使用 `isolation: "worktree"`
8. **收集与核对**：
   - 用子代理返回的 agentId 逐个等待结果
   - 核对覆盖面：是否每个输入都有结果、有无重复、结论是否冲突
   - 失败的子任务只重试失败的部分
9. **整合**：由主代理审阅后合并改动，再对整体执行一次 A 部分的自检。

## 注意事项 / 安全

- 子代理的权限与主代理相同。不要把需要用户确认的副作用操作（发布、删除、付款）交给子代理自行决定。
- 不要为了并行而牺牲正确性。存在共享状态时宁可串行。
- 自检报告要如实写明没有验证到的部分。

## 如何确认完成

自检清单每项都有结论，lint 和测试全部通过。并行任务的所有子任务结果都已收集、核对并整合，没有遗漏的输入。

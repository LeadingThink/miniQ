## 适用场景

- 需求只有一句话，例如"加个导出功能"，边界、验收标准或技术方案不明
- 改动会涉及 3 个以上文件或跨模块，直接写代码容易返工

一行修复、拼写修正等小事不适用，直接做即可。

## 前置条件

- 能读取项目代码（`glob` / `grep` / `file_read`）

## 步骤

### A. 澄清需求

1. **先看现状再提问**：
   - 用 `glob` / `grep` 找到相关模块、已有类似实现和测试目录
   - 用 `memory_search` 查项目约定，例如代码风格、测试命令、禁止事项
2. **一次问清关键问题**（`ask_user`），每轮最多 3 个，优先问会改变方案的问题：
   - 目标用户与使用场景
   - 输入与输出边界
   - 不做什么（non-goals）
   - 验收标准：怎样算做完
   - 每个问题附上你推荐的默认答案，方便用户直接确认
3. **发散方案**：给出 2–3 个可行方案，每个方案说明以下几点，并给出推荐：
   - 思路
   - 改动面
   - 风险
   - 工作量（S/M/L）
4. **收敛**：用户选定后，用一段话复述"要做什么 / 不做什么 / 验收标准"，得到确认。

### B. 写实施计划

5. **拆成小步**：每步都应能在一次提交内完成并单独验证，粒度约为 15–60 分钟的工作量。每步写明以下内容：
   - 要改的文件路径（精确到文件）
   - 具体改动：函数签名、数据结构
   - 先写哪个测试，预期先红后绿
   - 验证命令，例如 `npm test -- path`、`pytest tests/x.py -k name`、`cargo test name`
   - 依赖哪一步，哪些步骤彼此独立、可以并行
6. **落盘**（`file_write`）：写入 `docs/plans/<日期>-<主题>.md`，包含背景、决策、步骤清单（`- [ ]` 复选框）和风险与回滚方式。
7. **确认后执行**（`ask_user`）：计划得到认可后，按顺序执行：
   - 每完成一步就用 `file_edit` 勾选复选框
   - 可并行的独立步骤交给 `sp-review-dispatch` 技能分派
   - 每步编码按 `sp-tdd-debug` 的节奏进行

## 注意事项 / 安全

- 不要替用户做产品决策。有歧义就问，但不要连环追问，先给默认答案。
- 计划中的删除、迁移、对外发布等不可逆步骤要单独标注，执行前再次确认。
- 用户明确表示"别问了直接做"时，把假设写进计划顶部的"假设"一节，然后执行。

## 如何确认完成

需求复述已被确认，并且计划文件已写入，每步都有文件、测试和验证命令。

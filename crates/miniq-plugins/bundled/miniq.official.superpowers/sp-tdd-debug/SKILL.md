## 适用场景

- 新增或修改有明确输入输出的逻辑（TDD）
- 出现 bug、测试失败、线上报错或"时好时坏"的现象（系统化调试）

## 前置条件

- 知道项目测试命令：
  - 查看 `package.json` 的 scripts、`pyproject.toml`、`Makefile`、`Cargo.toml`
  - 也可以用 `memory_search` 查找

## 步骤

### A. TDD：红 → 绿 → 重构

1. **写一个失败的测试**（`file_edit` / `file_write`）：
   - 每次只写一个行为，测试名描述行为，例如 `returns_empty_list_when_no_orders`
   - 优先覆盖边界：空值、极值、错误输入
2. **确认它真的失败**（`shell_run`）：
   - 只运行这一个测试，例如 `npx vitest run path -t "name"`、`pytest path::test_name`、`cargo test name`、`go test ./pkg -run TestName`
   - 失败原因必须是"功能未实现"，而不是语法错误或导入错误
3. **写最少的实现让它通过**（`file_edit`），再运行同一条命令确认变绿。
4. **重构**：在保持绿色的前提下消除重复、改善命名，然后运行该模块的全部测试。
5. 回到第 1 步写下一个行为。全部完成后运行完整测试套件和 lint/类型检查。

### B. 系统化调试：复现 → 假设 → 验证

1. **收集事实**：
   - 用 `file_read` / `shell_run` 获取完整报错、堆栈、触发输入、环境（版本、系统）和最近改动（`git log -p -5 -- <file>`）
   - 不要只看最后一行错误
2. **稳定复现**：
   - 写一个最小复现：一个失败的测试或脚本（`file_write`），然后用 `shell_run` 运行确认
   - 偶发问题要记录复现率，例如循环 20 次，看失败几次
3. **列假设**：写出 2–4 个可能原因，按"可能性 × 验证成本"排序。每个假设写一个能区分真假的观察，例如某个变量在 X 处应为 Y。
4. **逐个验证**：
   - 用最便宜的手段验证：加日志或断言、二分法（`git bisect run <测试命令>`）、缩小输入、替换依赖版本
   - 一次只改一个变量
   - 记录每个假设的结果（成立或排除）
5. **修根因而不是症状**：
   - 修复后，第 2 步的复现测试应变绿，并保留为回归测试
   - 移除临时日志
6. **扩大验证**：
   - 运行完整测试套件
   - 用 `grep` 搜索同类模式，检查是否存在同类缺陷

## 注意事项 / 安全

- 验证假设时，不在生产环境或真实数据上做破坏性实验。必须触达外部系统时先 `ask_user`。
- 3 轮假设都被排除时，停下来向用户汇报已排除的方向和下一步建议，不要无休止地乱改。
- 不要为了让测试变绿而修改测试的断言，除非确认测试本身是错的，并向用户说明。

## 如何确认完成

TDD：每个新行为都有先失败后通过的测试，并且全套测试通过。调试：有能稳定复现的回归测试，修复后通过，并能用一两句话说清根因。

## 适用场景

用户只有一个游戏点子（"做个像 Flappy Bird 的太空版"），或已有原型但缺少清晰的设计文档。产出一份可直接指导原型开发的 GDD（Game Design Document）。

## 前置条件

- 无需外部账号。文档写入用户项目目录（默认 `docs/GDD.md`）。

## 步骤

1. **澄清核心体验**（`ask_user`）：一次性问清以下几项，给出默认值供选择：
   - 类型/参考作品
   - 目标平台（桌面浏览器 / 移动浏览器 / 两者）
   - 单局时长
   - 操作方式（键盘、鼠标、触屏）
   - 美术风格（像素、扁平、低多边形 3D）
   - 是否需要音乐和音效
2. **（可选）调研参考**（`web_search` / `web_fetch`）：查 1–3 个同类游戏的核心循环与操作手感描述。搜到的内容只作参考，不照抄。
3. **选择技术栈**，写进文档并说明理由：
   - 2D 动作、平台跳跃、带物理的游戏用 **Phaser 3**（`npm i phaser`）
   - 3D 或需要相机与光照的游戏用 **Three.js**（`npm i three`）
   - 极简规则类（贪吃蛇、2048、益智）用 **原生 Canvas 2D**，没有依赖
   - 构建工具统一用 **Vite**
4. **写 GDD**（`file_write`，路径 `docs/GDD.md`），包含以下章节：
   - 一句话卖点
   - 核心循环：输入 → 反馈 → 奖励
   - 操作表
   - 胜负条件与计分
   - 难度曲线 / 关卡表：至少 3 关，列出参数，例如速度、敌人数量
   - 实体清单：玩家、敌人、道具，以及各自的属性
   - 美术素材清单：文件名、尺寸、用途、`generate_image` 提示词草稿
   - 音频清单：BGM 与音效，附 `generate_music` 提示词草稿
   - 技术选型
   - 里程碑：M1 可玩灰盒 → M2 素材替换 → M3 打磨与发布
5. **确认**（`ask_user`）：把 GDD 要点发给用户，确认后再进入 `game-prototype` 技能。

## 注意事项 / 安全

- 不使用受版权保护的角色、名称、音乐。参考作品只借鉴玩法，不复制美术。
- 数值（速度、重力、生成间隔）集中写在 GDD 的"调参表"里，方便原型阶段直接映射为常量。

## 如何确认完成

`docs/GDD.md` 已写入，包含核心循环、操作表、关卡参数、素材与音频清单和技术选型，并且用户已确认。

# 硬 bug 诊断循环

## 适用场景
- "这个接口偶尔 500，查不出来。"
- "升级依赖后首屏慢了 2 秒。"
- "测试在 CI 上挂、本地过，帮我诊断。"

不适用：报错信息已经直接指出行号和原因的简单错误——直接修。

## 前置条件
- 读 `GLOSSARY.md`（存在时）了解模块术语；查 `docs/adr/` 看相关决定。
- **脱敏规则**：本技能会展示命令、输出和抓包。所有密钥先替换为 `<已脱敏>`；回路脚本通过环境变量读凭证，不写进脚本正文；抓包只引用带信号的行。脱敏后信息不够，就直说并向用户要。

## 阶段 1：建反馈回路（本技能的核心）

**有一个针对这个 bug 能变红的信号，就一定能找到原因；没有，看代码再久也没用。** 在这一步投入不成比例的精力。

可选手段（按优先级）：
1. 失败测试：单元 / 集成 / e2e，哪层能碰到 bug 用哪层。
2. `curl` 或 HTTP 脚本打本地 dev server。
3. CLI + 固定输入，diff stdout 与已知正确快照。
4. 无头浏览器脚本（`browser_automation` 或 Playwright）驱动 UI，断言 DOM / console / 网络。
5. 回放抓到的真实请求 / 事件日志。
6. 一次性最小 harness：只起一个服务、mock 依赖、一个函数调用。
7. 属性 / 模糊循环：1000 个随机输入找失败模式。
8. 二分 harness：bug 出现在两个已知状态之间时，自动化"切到 X → 检查"，交给 `git bisect run`。
9. 差分回路：同一输入跑旧版 vs 新版，diff 输出。
10. 人工循环（最后手段）：必须人点击时，写一个 bash 脚本按步骤提示用户操作并收集输出。

**收紧回路**：能更快吗（缓存初始化、缩小范围）？信号更尖吗（断言具体症状，不是"没崩"）？更确定吗（固定时间、种子、文件系统、网络）？2 秒确定性回路是武器，30 秒偶发回路几乎没用。

**偶发 bug**：目标不是干净复现而是**提高复现率**：循环 100 次、并行、加压、缩时间窗、插 sleep。50% 复现可查，1% 不可查。

**完成标准**：你能说出**一条命令**（已经至少跑过一次，贴出命令和脱敏输出），它：
- [ ] 能变红：走到真实 bug 路径，断言用户描述的**那个**症状。
- [ ] 确定：每次结论一致（偶发 bug 则复现率已固定在高位）。
- [ ] 快：秒级。
- [ ] 可无人值守运行。

**没有这条命令，不进阶段 2。** 发现自己在"读代码找理论"就停下。

实在建不出来：明说，列出尝试过的手段，向用户要 (a) 能复现的环境 (b) 脱敏的 HAR / 日志 / dump / 带时间戳录屏 (c) 临时在生产加探针的许可。

## 阶段 2：复现 + 最小化
- 跑回路，看它变红。确认是**用户说的那个**失败，不是旁边另一个。
- 记下精确症状（错误原文、错误输出、耗时）。
- **最小化**：一次去掉一个元素（输入、调用方、配置、数据、步骤），每去一个重跑；留下的每个元素都是"去掉就变绿"的。最小复现 = 阶段 3 的假设空间更小 + 阶段 5 的干净回归测试。

## 阶段 3：假设
- 列 **3–5 个有排序的假设**后再验证任何一个，避免锚定第一个想法。
- 每个假设可证伪："如果 X 是原因，那么改 Y 会让 bug 消失 / 改 Z 会让它更糟。"说不出预测的假设是感觉，丢掉或磨尖。
- **先把排序表给用户看**（`ask_user`，可不阻塞）：用户常有"我们刚好改了 #3"这类信息。

## 阶段 4：插桩
- 每个探针对应阶段 3 的一个预测。**一次只改一个变量。**
- 工具优先级：调试器 / REPL 断点 > 边界处的定向日志 > 禁止"全打日志再 grep"。
- **所有调试日志加统一前缀**，如 `[DEBUG-a4f2]`，最后一条 `file_grep` 清掉。
- 性能问题：日志通常没用。先建基线（计时 harness、`performance.now()`、profiler、查询计划），再二分。先测后改。

## 阶段 5：先写回归测试，再修
- 只在**正确的缝**上写回归测试：测试要以 bug 真实发生的方式触发它。缝太浅（需要多调用方却只测单个）会给假信心。
- **没有正确的缝本身就是发现**：记录下来，这说明架构阻止了把 bug 锁死，交给 `architecture-review`。
- 有缝：最小复现 → 失败测试 → 看它失败（若用改代码制造红，diff 证明改动生效）→ 修 → 看它通过 → 用阶段 1 回路跑**原始未最小化**场景。

## 阶段 6：清理
- [ ] 阶段 1 回路对原始场景变绿。
- [ ] 回归测试通过（或已记录"无缝"）。
- [ ] `file_grep '\[DEBUG-'` 无命中。
- [ ] 一次性 harness 已删或移到明确标注的 debug 目录。
- [ ] 正确的假设写进提交 / PR 说明，让下一个人学到。

## 注意事项 / 安全
- 修改生产配置、加生产探针前 `ask_user`。
- 不把真实用户数据写进测试固件；脱敏或合成。

## 如何确认完成
阶段 6 五项全勾；回复中贴出回路命令、正确假设、回归测试路径。

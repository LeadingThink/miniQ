# 一次性原型

原型是**用来回答一个问题的一次性代码**。问题决定形状。

## 适用场景
- "订单状态流转我不太确定，做个能点的看看。"
- "设置页出三个风格差异大的方案，我挑。"
- "先验证一下这个算法在边界情况下对不对。"

## 前置条件
- 先读 `miniq.official.visual-language/visual-language-core/SKILL.md`：UI 原型也要用统一令牌，但**不做打磨**。
- 定清问题是"逻辑对不对"还是"长什么样"。不清楚且用户在线：`ask_user` 一个问题。用户不在线：看周边代码——后端模块 → 逻辑；页面/组件 → UI，并在原型顶部写明这个假设。

## 分支 A：逻辑原型（"这个状态模型/逻辑对吗？"）
产出：**一个可双击打开的 HTML 文件**，非开发者也能操作。
1. 从代码或描述里抽出状态、事件、转移、不变量，写成一张表放 HTML 顶部。
2. 页面结构：
   - 左侧"自由操作区"：每个事件一个按钮。
   - 右侧"当前状态"：完整状态对象 JSON 高亮显示，每次操作后刷新。
   - 底部"引导走查"标签页：预设 3–6 个难在纸上推的场景（并发、回退、超时、重复提交），每个场景一键按步播放并高亮违反不变量的地方。
3. 状态只在内存；用 `file_write` 写 `原型/<问题>-逻辑.html`（放在被验证模块旁边时文件名加 `.prototype.html` 后缀）。
4. 用 `browser_automation` 本地打开（需 http 服务：`python3 -m http.server`）截图核对；把每个走查场景的最终状态贴给用户。

## 分支 B：UI 原型（"该长什么样？"）
产出：**同一路由下 3–5 个差异极大的方案**，通过 URL 参数 `?variant=a|b|c` 切换，页面底部有悬浮切换条。
1. 每个方案至少在 2 个维度上不同（布局结构 / 信息密度 / 导航方式 / 视觉风格），不是换个颜色。
2. 遵循项目已有的路由约定；没有项目时写独立 HTML 到 `原型/<页面>-ui.html`。
3. 用 `browser_automation` 对每个 variant 截一张图（桌面 1280×800 + 移动 390×844），`view_image` 核对，整理成"方案对比表：方案 / 一句话特点 / 适合谁 / 风险"。
4. `ask_user` 让用户选（可多选"A 的布局 + C 的配色"）。

## 两条分支共同规则
1. **从第一天就是一次性**，并且一眼能看出来：文件名含 `prototype`/`原型`，顶部大字注明"原型，勿用于生产"。
2. **启动零思考**：一条命令或双击打开。
3. **默认不持久化**：持久化是原型要验证的对象，不是依赖。必须碰数据库时用名字里带 `PROTOTYPE_WIPE_ME` 的临时库。
4. **不打磨**：无测试、无错误处理（能跑即可）、无抽象。
5. **把状态露出来**：每次操作后完整打印相关状态。
6. **收尾**：
   - 把验证过的决定写进正式代码或 ADR。
   - 原型本身作为**一手资料**保留：`git switch -c prototype/<问题>` 提交到独立分支，不进主干；在实施 issue / 计划里留一个指向该分支的链接。
   - 把"问题 + 结论"写进 issue 或提交说明。

## 注意事项 / 安全
- 原型里不要放真实用户数据或密钥。
- 不要让原型代码被 import 进生产模块；放在 `原型/` 或 `*.prototype.*`。

## 如何确认完成
用户对"问题"给出了明确结论；结论已记录；原型已提交到独立分支或用户同意删除。

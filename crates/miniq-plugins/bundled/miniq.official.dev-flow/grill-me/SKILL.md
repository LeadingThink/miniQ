# 追问式需求对齐

## 适用场景
- "我想做一个 X，你先问我问题，问到清楚为止。"
- "这个方案有没有漏洞？帮我盘一下。"
- "需求我只有一句话，你来追问我补全。"
- 动手写代码、写文档、做设计之前，用户和 miniQ 对"要做什么"还没有共识。

不适用：用户已经给了完整规格并说"直接做"；或问题是事实查询而非决策。

## 前置条件
- 读过工作区里已有的上下文：`GLOSSARY.md`/`术语表.md`、`docs/adr/`、相关 README。用 `file_glob` 和 `file_read`。
- 这是一个对话型技能。它不产出文件，除非用户要求把结论落成文档（交给 `writing-plans` 或 `research-report`）。

## 步骤

1. **建树**：把用户的目标看成一棵**决策树**：每个决定下面挂着依赖它的子决定。先在心里列出根节点下第一层的分支。
2. **算前沿**：**前沿** = 所有前置条件已经确定、现在就能问而不用猜的问题。只问前沿，不问依赖于本轮未决问题的问题。
3. **一轮提问**：把整个前沿一次问完。每个问题编号，给出**你的推荐答案**，并把问题措辞成"回答'是'就等于接受推荐"。格式：

   ```
   ❓ **Q1 · <问题标题>**
   <问题正文；可以给 2–4 个选项>
   ➡️ 推荐：<你的推荐及一句话理由>

   ---

   ❓ **Q2 · <问题标题>**
   ……
   ```

   用 `ask_user` 发送这一轮（问题多于 3 个时，用 `questions` 数组一次问多项；选项用 `options`，推荐项放第一个并在 `default` 里写明）。
4. **事实自己查，决定留给用户**：某个问题需要环境事实（文件是否存在、现有接口长什么样、依赖版本）时，不要问用户，用 `file_grep`/`file_read`/`shell_run` 自己查；查询耗时且独立时用 `agent_run`（`runInBackground: true`）去查，不阻塞其他问题。只有依赖该事实的问题推迟到下一轮。
5. **收答案，重算前沿**：用户每答一轮，已决定的节点把前沿往外推、解锁新问题。重复第 2–4 步。
6. **终止条件**：前沿为空——每个分支都走过，没有任何被默默假设的事。此时用 3–8 条要点复述"我们达成的共识"，`ask_user` 请用户确认。
7. **确认后才动手**：用户确认前不开始实施。确认后按需切到 `writing-plans`、`test-driven-development` 或具体领域技能。

## 提问质量
- 每轮 3–7 个问题。少于 3 个说明前沿没算全；多于 7 个说明有些问题互相依赖，拆到下一轮。
- 问"非此即彼"的问题时列出选项和各自代价，不问开放式的"你觉得呢"。
- 给推荐答案时写理由，让用户能快速判断是否同意。
- 用户的答案出现新术语时，顺手确认定义，并建议写入 `GLOSSARY.md`（存在时用 `file_edit` 追加）。
- 用户说"不知道/都行"时，把你的推荐当作暂定答案并明确标注"暂定"，继续往下走，最后在共识摘要里单独列出所有暂定项。

## 注意事项 / 安全
- 不要在一轮里混入"我已经决定要这样做"的陈述；所有决定都要经用户点头。
- 不要为了显得周到而问无关问题；每个问题必须能改变后续做法。
- 涉及费用、对外发布、删除数据的决定，在共识摘要里单独加粗标出。

## 如何确认完成
用户对共识摘要明确回复"确认/可以/对"，且摘要里没有未标注的假设。

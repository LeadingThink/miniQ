## 适用场景

用户说"帮我把这个页面调得更好看"、"手机上布局乱了"、"检查一下可访问性"、"按钮没有 hover 效果"。前提是项目可以在本地运行。

## 步骤（写明每步用哪个工具）

1. 明确范围：用 `ask_user` 确认要打磨的页面/组件、目标设备、是否有设计稿（有则用 `view_image` 查看设计稿）以及不能改动的部分（品牌色、既有设计系统）。
2. 摸清样式体系：用 `file_glob` / `file_read` 查看样式方案（CSS Modules、Tailwind 配置、CSS 变量、组件库主题），用 `file_grep` 找重复的魔法数值（如各处不同的 `margin: 13px`、硬编码颜色）。
3. 建立基线：用 `shell_run` 后台启动 `npm run dev`；用 `browser_automation` 打开页面，分别在 375、768、1440 宽度下 `screenshot`，保存为"修改前"基线，并用 `view_image` 记录问题清单。
4. 逐类打磨（`file_edit` 小步修改，每类改完即复查）：
   - 排版与间距：统一到间距刻度（如 4/8 的倍数），标题层级清晰，正文行高约 1.5，每行长度适中。
   - 颜色与对比度：普通文字对比度不低于 4.5:1，颜色提取为 CSS 变量或主题 token。
   - 交互状态：按钮/链接补齐 `:hover`、`:focus-visible`、`:active`、`disabled` 状态；加载与空状态有提示。
   - 可访问性：图片有 `alt`；表单控件关联 `<label>`；图标按钮有 `aria-label`；使用语义标签（`button` 而非可点击 `div`）；键盘 Tab 顺序合理。
   - 响应式：用弹性布局和 `clamp()`、`minmax()` 代替固定宽度；消除横向滚动；触控目标不小于 44×44px。
   - 动效：过渡时长 150–300ms，并尊重 `prefers-reduced-motion`。
5. 复查：用 `browser_automation` 在同样三个宽度重新截图，用 `view_image` 与基线逐张对比，确认问题已修复且没有引入新的错位；用键盘 Tab 走一遍主要交互。
6. 运行项目已有的 lint / 测试 / 构建（如 `npm run lint`、`npm run build`）确保未破坏功能。
7. 用 `git_diff` 汇总改动，向用户列出"问题 → 修改 → 前后截图路径"对照表。

## 注意事项 / 安全

- 保持现有设计语言，不擅自更换品牌色、字体或组件库；较大的视觉改版先征得用户同意。
- 每次只改一类问题，便于回退和审查。
- 不删除现有功能或文案；文案调整需用户确认。
- 结束前停止后台开发服务器。

## 如何确认完成

三个视口的修改后截图均无溢出和错位，问题清单中的每一项都有对应修改或说明，构建通过。

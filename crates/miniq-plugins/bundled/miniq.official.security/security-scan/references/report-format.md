# 扫描报告（report.md）结构

`findings_report.py --format markdown` 生成骨架，代理补写叙述部分。报告面向两类读者：需要决策的负责人（看摘要）和需要修复的工程师（看详情）。

## 章节

1. **标题与元数据**：扫描编号、目标路径、版本、差异基线（如有）、范围、生成时间。
2. **执行摘要**（代理补写，≤10 行）
   - 一句话结论：本次最重要的风险是什么、谁能利用、后果是什么。
   - 严重度分布与整体态势（例如"鉴权层整体健全，但文件处理模块缺少路径约束"）。
   - 首要行动 1–3 条，每条对应 finding 编号。
3. **统计**：各严重度数量。
4. **问题一览**：编号、严重度、置信度、状态、标题、主位置。
5. **详情**：每条 finding 一个小节，顺序固定——元数据、概述、根因、位置、前置条件、攻击路径、影响/可能性、验证、已核查反证、修复建议、参考。
6. **覆盖范围与局限**（代理补写）
   - 审查过的攻击面及结论（来自 coverage.json 的 surfaces）。
   - 跳过或部分审查的内容与原因。
   - 未能验证的假设（例如"假设生产环境开启了反向代理鉴权"）。
   - 未运行的工具（依赖审计、动态测试等）。
7. **附录**（可选）：不可达的依赖漏洞列表、被排除的候选及排除理由摘要、术语表。

## 写作规则

- 标题写"谁能对什么做什么"：好例子"任意登录用户可读取其他租户的发票 PDF"；差例子"IDOR 漏洞"。
- 先事实后判断；推断明确标注"推断"或"未验证"。
- 代码片段只截取关键 3–10 行，并注明路径与行号。
- 不夸大：没有证据证明可远程利用时，不写"远程代码执行"。
- 不暴露密钥、个人数据；截图或日志中的敏感值打码。
- 语气客观、可操作，避免"显然""非常危险"之类形容。

## 零发现报告

依然输出完整结构，统计全 0，并在执行摘要中写清：审查范围、重点攻击面、为何认为没有达到报告门槛的问题、残余风险与建议（如"建议对上传模块做动态测试"）。

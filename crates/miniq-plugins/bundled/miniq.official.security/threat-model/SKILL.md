## 适用场景

用户说"帮我做威胁建模"、"这个新功能有哪些安全风险"、"写一份 STRIDE 分析"。输入可以是代码仓库、架构文档或用户口头描述。产物是一份可评审的 Markdown 文档。

## 步骤（写明每步用哪个工具）

1. 收集背景：
   - 有仓库时，用 `file_glob` / `file_read` 看 README、架构文档、部署配置（Dockerfile、k8s、`*.tf`），用 `file_grep` 找外部接口与第三方调用。
   - 有设计文档时用 `doc_read` 读取。
   - 信息不足时用 `ask_user` 询问：用户类型、部署位置、处理哪些敏感数据、合规要求。
2. 描述系统：列出组件（前端、API、数据库、队列、第三方服务）、参与者（匿名用户、登录用户、管理员、内部服务）。
3. 识别资产：用户数据、凭据、业务数据、可用性、审计日志等，并标注敏感级别。
4. 画数据流与信任边界：用 Mermaid `flowchart` 在文档中描述数据流，标明每条跨越信任边界的连线（如 互联网→API、API→数据库、服务→第三方）。
5. 按 STRIDE 对每个跨边界的元素逐项分析：
   - S 仿冒（Spoofing）：身份认证是否可伪造。
   - T 篡改（Tampering）：数据传输/存储是否可被修改。
   - R 抵赖（Repudiation）：关键操作是否有可追溯日志。
   - I 信息泄露（Information Disclosure）：错误信息、日志、存储是否泄露敏感数据。
   - D 拒绝服务（Denial of Service）：限流、资源上限、超时。
   - E 权限提升（Elevation of Privilege）：越权、注入导致的权限扩大。
6. 为每个威胁评估可能性（高/中/低）和影响（高/中/低），给出风险等级，并写缓解措施与当前状态（已有 / 缺失 / 部分）。
7. 用 `file_write` 输出 `threat-model.md`，结构：范围与假设 → 系统概述 → 资产 → 数据流图（Mermaid）→ 威胁表（编号、STRIDE 类别、元素、描述、风险、缓解、状态）→ 优先处理清单 → 未覆盖的问题与待确认事项。
8. 把待确认的假设列给用户，根据反馈更新文档。

## 注意事项 / 安全

- 明确写出假设，不要把猜测当事实；不确定的部分放入"待确认事项"。
- 文档中不写入真实密钥、内部 IP 或账号，必要时用占位符。
- 威胁建模是设计层分析，不做任何主动扫描或攻击。

## 如何确认完成

每个跨信任边界的数据流都至少经过一次 STRIDE 分析，高风险项都有缓解建议，文档可直接用于团队评审。

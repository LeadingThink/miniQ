## 适用场景

用户说"帮我做个安全审查"、"这段代码有没有安全问题"、"上线前查一下漏洞"。可以审查整个仓库，也可以只审查当前改动（`git_diff`）。本技能只读分析，默认不修改代码。

## 步骤（写明每步用哪个工具）

1. 确定范围：用 `ask_user` 确认审查整个仓库、某个目录还是当前改动；了解部署形态（Web 服务、桌面应用、CLI、库）。
2. 摸清技术栈：用 `file_glob` 找 `package.json`、`Cargo.toml`、`requirements.txt`、`go.mod`、`pom.xml` 等，用 `file_read` 读取框架与依赖。
3. 定位攻击面：用 `file_grep` 搜索入口点——路由定义（`app.get(`、`@app.route`、`Router`）、命令行参数解析、文件上传、反序列化、外部请求。
4. 按类别逐项检查（每类用 `file_grep` 找线索，再用 `file_read` 看上下文确认，不凭关键字下结论）：
   - 注入：SQL 字符串拼接、`exec`/`eval`/`subprocess(..., shell=True)`/`child_process.exec`、模板注入。
   - XSS：`innerHTML`、`dangerouslySetInnerHTML`、`v-html`、未转义输出。
   - 认证与授权：缺少鉴权中间件、对象级越权（按 id 取数据未校验归属）、会话/JWT 配置（过期、签名算法）。
   - 敏感数据：硬编码密钥（可配合 `secret-scan`）、日志中打印令牌或个人信息、明文存储密码（应使用 bcrypt/argon2）。
   - 不安全配置：CORS `*` 且带凭据、调试模式开启、缺少安全响应头、TLS 校验被关闭（`verify=False`、`rejectUnauthorized: false`）。
   - 路径与文件：路径穿越（用户输入拼路径）、不受限的上传类型与大小、SSRF（用户控制的 URL 被服务端请求）。
   - 依赖：在用户同意后用 `shell_run` 运行 `npm audit --omit=dev`、`pip-audit`、`cargo audit`（工具存在时）。
5. 为每个发现评级：严重 / 高 / 中 / 低 / 信息，依据可利用性与影响；标注置信度（确认 / 疑似）。
6. 用 `file_write` 输出 `security-review.md`：摘要（各级数量）→ 发现列表（标题、级别、位置 `文件:行号`、描述、利用场景、修复建议与示例代码）→ 已检查但未发现问题的类别 → 局限性说明。
7. 用户希望修复时，再逐项用 `file_edit` 修改并用 `git_diff` 展示。

## 注意事项 / 安全

- 报告中引用密钥时只保留前 4 位并打码，不回显完整值。
- 不要对线上系统做主动攻击性测试；仅做静态审查，动态验证需用户明确授权且限于其自有环境。
- 区分"确认漏洞"和"潜在风险"，避免夸大；也不要因为没搜到就断言"安全"。
- 修改鉴权、加密相关代码前先向用户确认。

## 如何确认完成

报告覆盖上述全部类别，每条发现都有具体位置和可执行的修复建议，并写明审查范围与局限。

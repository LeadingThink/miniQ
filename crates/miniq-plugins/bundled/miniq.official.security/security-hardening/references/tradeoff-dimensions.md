# 加固方案权衡维度

用途：在同一个加固机会下比较 2–4 个**实质不同**的方案（不是同一方案的强弱版本）。每个方案在每个维度上给出档位和一句话理由，理由必须能追溯到证据编号（E-xx）或明确标为假设（A-xx）。

## 1. 档位约定

统一用五档，箭头方向对所有维度一致——**越靠右越好**：

| 符号 | 含义 |
| --- | --- |
| `−−` | 明显变差 / 代价很高 |
| `−` | 略差 / 代价中等 |
| `0` | 与现状持平 / 无明显影响 |
| `+` | 略好 / 代价较低 |
| `++` | 明显改善 / 几乎无代价 |

"代价类"维度（工作量、性能、兼容性）同样按"越靠右越好"标注：工作量极小记 `++`，而不是"工作量 ++ 表示很多"。表头注明这一点，避免读者误读。

不要把档位加总成一个分数：维度之间不可通约，汇总分会掩盖"一个致命缺点"。推荐结论靠叙述权衡，而不是算术。

## 2. 安全维度

| 维度 | 要回答的问题 | 判定参考 |
| --- | --- | --- |
| **消除的问题类别** | 方案让哪一类问题"不可能发生"，还是只是"更难发生"？ | `++`：结构上不可表达（类型、API 形状、默认拒绝）；`+`：集中检查但可被绕过；`0`：仅修补已知实例 |
| **覆盖面** | 现有与未来的入口有多少比例会自动受到保护？ | 用证据列出的入口数计算；新入口是否"默认受保护" |
| **绕过难度** | 开发者是否可能不经意绕过？攻击者能否找到未经过控制的路径？ | 看是否存在旁路 API、原始访问、配置开关 |
| **失效方式** | 控制出错时是拒绝（fail-closed）还是放行（fail-open）？ | fail-open 最多记 `0` |
| **纵深** | 是否与其他层形成独立的第二道防线？ | 与已有控制重复同一假设的不算纵深 |
| **可观测性** | 违规尝试能否被记录、告警、审计？ | 有结构化事件与指标记 `+` 以上 |
| **对已知 findings 的闭合** | 证据表中关联的 findings 有几个会被该方案关闭？ | 逐个列出 F-xxx，未关闭的写入残余风险 |

## 3. 工程维度

| 维度 | 要回答的问题 | 判定参考 |
| --- | --- | --- |
| **实施工作量** | 需要改多少模块、多少调用点、多少团队？ | 以调用点清单为依据估计：<10 个调用点记 `+`，跨团队记 `−` 或更低 |
| **迁移难度** | 能否渐进迁移？是否需要一次性切换？ | 支持"新旧并存 + 逐步切换"记 `+` |
| **兼容性影响** | 是否会拒绝当前合法的请求/数据/客户端？ | 需列出已知会受影响的合法用例 |
| **性能与成本** | 额外延迟、资源、基础设施费用？ | 有测量或基准时写数字；否则标为假设 |
| **开发体验** | 正确用法是否比错误用法更容易？ | 正确路径更短、有 lint/类型帮助记 `+` |
| **可测试性** | 能否写出稳定的测试证明不变量成立？ | 能做"全入口枚举测试"或静态检查记 `++` |
| **运维复杂度** | 新组件、新配置、新密钥、新故障模式？ | 新增需要值守的组件记 `−` |
| **可逆性** | 上线后发现问题能否快速回退？ | 有功能开关、影子模式记 `+` |

## 4. 组织与生命周期维度（按需）

| 维度 | 要回答的问题 |
| --- | --- |
| **所有权清晰度** | 方案落地后，这个控制由谁维护？ |
| **与既有方向一致** | 是否与仓库现有框架、平台规划一致，还是引入第二套机制？ |
| **依赖风险** | 是否引入新第三方依赖？其维护状况、许可证、供应链风险？ |
| **合规** | 是否满足或影响已知的合规要求（审计日志保留、数据驻留）？ |

## 5. 比较表模板

```markdown
| 维度（越靠右越好） | 方案 A：现状加补丁 | 方案 B：集中中间件 | 方案 C：类型化访问层 |
| --- | --- | --- | --- |
| 消除的问题类别 | 0 仅已知实例（E-01） | + 统一检查，可绕过原始查询（E-04） | ++ 未授权查询不可表达（A-02） |
| 覆盖面 | − 17 个入口中 12 个（E-02） | + 路由层全覆盖，后台任务不覆盖（E-05） | ++ 所有数据访问 |
| 失效方式 | − 漏写即放行 | + 默认拒绝 | ++ 编译期失败 |
| 实施工作量 | ++ 5 处调用点 | + 1 个中间件 + 配置 | −− 约 140 个查询需迁移（E-06） |
| 兼容性影响 | ++ 无 | 0 需为公开接口加豁免 | − 内部 API 签名变化 |
| 可逆性 | ++ | + 开关控制 | − |
```

每个单元格格式：`档位 + 一句理由 +（证据/假设编号）`。

## 6. 使用规则

1. **先定不变量再比较**：维度评判的是"方案对期望不变量的满足程度"，没有不变量就无从比较。
2. **至少一个方案挑战推荐**：包含一个"最小改动"方案作为基线，除非它显然不能满足任何不变量。
3. **标出决定性维度**：在表下写"本机会的决定性维度是 X 和 Y，因为……"，读者据此理解推荐为何成立。
4. **不隐藏致命缺点**：任何 `−−` 必须在推荐小节中正面回应（接受、缓解或因此不选）。
5. **区分测量与判断**：性能、工作量写明是测量、估计还是假设；假设进入开放问题。
6. **避免伪精确**：不要写"安全性提高 37%"。
7. **结合现状风险**：若现状风险高（活跃利用、重复出现 findings），可接受更高工程代价，并在推荐中写明这一取舍。

## 7. 常见反模式

- 三个方案其实是一个方案的"轻 / 中 / 重"三档。
- 所有维度都给推荐方案 `+`，给其他方案 `−`（稻草人比较）。
- 用"最佳实践"作为理由而不指向本仓库的证据。
- 只比较安全维度，忽略迁移与运维代价，导致推荐无法落地。
- 把"增加一层 WAF/过滤"当作消除问题类别。

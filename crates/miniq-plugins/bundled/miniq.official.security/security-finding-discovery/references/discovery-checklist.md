# 发现检查清单

本清单供父代理与各调查员逐项对照。它不是"必须全部命中"的列表，而是提醒不要漏掉某一类攻击面。每一项都要回到具体代码：找到入口、找到控制、找到汇点，再判断影响。

## 0. 开工前

- 读完威胁模型中与本任务包相关的攻击者画像、资产、信任边界，写一句话概括"谁在攻击什么"。
- 确认适用的 SECURITY.md 摘要：哪些输入被声明为可信、哪些类别被排除、哪些类别被要求重点关注。
- 确认可用的检索命令（`rg` / `git grep` / `grep -rn`）。
- 明确本任务包的文件边界；越界发现可以记录，但标注"越界线索"交父代理处理。

## 1. 入口枚举（source）

| 入口类型 | 典型线索 | 要确认的事 |
| --- | --- | --- |
| HTTP 路由 | 路由表、装饰器、控制器、`app.get/post`、`@RequestMapping`、`http.HandleFunc` | 路径、方法、中间件链、是否需要登录、参数绑定方式 |
| GraphQL / RPC | resolver、schema、`.proto`、gRPC service | 字段级鉴权、批量查询、内省是否开放 |
| 消息与队列 | consumer、subscriber、webhook 接收端 | 消息来源是否可信、签名校验 |
| 文件输入 | 上传、导入、解析器、归档解压 | 文件名、内容、嵌套结构谁能控制 |
| CLI / 环境变量 | argparse、flag、`os.environ` | 在本威胁模型中调用者是否可信 |
| 客户端 / 前端 | DOM 写入、`postMessage`、深链接、Electron IPC | 跨源、跨进程的数据是否被当作可信 |
| 插件 / 扩展 / Agent | 插件加载、MCP 工具、提示词拼接 | 不可信数据能否驱动高权限动作 |
| CI / 构建 | `.github/workflows`、Dockerfile、安装脚本 | `pull_request_target`、未固定版本、密钥暴露给 fork |
| 存储回流 | 数据库/缓存中他人写入的数据再被渲染或执行 | 二阶注入、存储型 XSS |

## 2. 控制检查（control）

- 认证：路由是否挂了认证中间件？是否存在"可选登录"、白名单路径、调试开关绕过？
- 授权：对象级（这条记录属于当前用户/租户吗？）、功能级（这个角色能调这个接口吗？）、字段级（能否改自己的角色、租户、邮箱验证状态？）。
- 输入校验：类型、长度、范围、格式；校验发生在使用之前还是之后；是否对解码/规范化之后的值校验。
- 输出编码：模板是否默认转义；是否有 `safe`、`dangerouslySetInnerHTML`、`v-html`、`|raw` 等显式绕过。
- 路径控制：`realpath`/`normalize` 后是否再次检查是否位于允许根目录内；符号链接。
- 网络目标控制：URL 白名单是否在重定向后仍生效；是否能访问内网、元数据地址、`file://`。
- 加密与令牌：签名是否校验、算法是否固定、过期是否检查、比较是否常量时间、随机数来源。
- 速率与资源：递归深度、大小上限、超时、分页上限。
- 失败方式：异常被吞后是否"默认放行"（fail-open）。

## 3. 汇点清单（sink）

| 类别 | 常见汇点 |
| --- | --- |
| 命令/代码执行 | `subprocess(shell=True)`、`os.system`、`exec`、`eval`、`child_process.exec`、`Runtime.exec`、模板引擎求值 |
| 查询注入 | 字符串拼接 SQL、ORM `raw`/`extra`、NoSQL 操作符注入、LDAP/XPath 拼接 |
| 反序列化 | `pickle.loads`、`yaml.load`（非安全加载器）、Java 原生反序列化、带类型标签的 JSON 库 |
| 模板注入 | 用户可控模板字符串交给 Jinja/Freemarker/Velocity/Handlebars 渲染 |
| 文件系统 | `open`/`send_file`/`sendFile` 接收拼接路径、解压写文件、上传落盘 |
| 外部请求 | `requests.get(url)`、`fetch(url)`、`HttpClient`、图片/文档代理、webhook 回调 |
| XML | 未禁用外部实体的解析器、XSLT 处理 |
| 浏览器端 | `innerHTML`、`document.write`、`location = 用户值`、`postMessage` 无源校验 |
| 状态变更 | 删除、转账、改权限、改配置、邀请成员、重置密码 |
| 敏感输出 | 日志写入令牌、错误回显堆栈与配置、接口返回多余字段 |

## 4. 类别速查

- 越权/IDOR：按 ID 取对象后是否比较归属；批量接口、导出接口、管理接口最容易漏。
- 认证缺陷：会话固定、登录后未轮换会话、重置令牌可预测或不过期、OAuth `state`/`redirect_uri` 校验、JWT `alg=none` 或未校验签名。
- 业务逻辑：负数/超大金额、重复提交、状态机跳步、竞态（先检查后使用）。
- CSRF：基于 Cookie 的状态变更接口是否有令牌或 SameSite 保护；JSON 接口是否接受简单请求的 Content-Type。
- 开放重定向：只在能串联令牌泄露或钓鱼升级时才有价值，单独出现时初判低。
- 信息泄露：调试端点、源码映射、备份文件、详细错误；需要说明泄露了什么敏感物。
- 供应链与 CI：工作流里用不可信输入拼命令（`${{ github.event.* }}`）、向 fork 暴露密钥、未固定第三方 action。
- Agent/LLM：外部内容进入提示后能否触发工具调用、文件写入、网络外发。

## 5. 差异模式

- 范围是"变更 + 被变更影响的代码"。对每个 hunk 问：它新增/修改了入口、控制还是汇点？
- 删除或弱化控制（去掉鉴权装饰器、放宽正则、把 `safe_load` 改成 `load`）是高价值信号，即使汇点本身未变。
- 新增入口要沿调用链走到汇点，哪怕汇点在未变更文件中。
- 修改汇点要反向找所有调用方，确认是否有新的攻击者可达路径。
- 不因"这是旧问题、不是本次引入"就丢弃：标注 `reasoning` 中"既有问题，本次变更使其可达/未改变"，由后续阶段决定是否报告。
- 纯重命名、格式化、测试代码、文档变更可快速标 `no_issue`，但要在 coverage 写明理由。

## 6. 收尾自查

- 每个疑点都写出了 source / control / sink / impact 四项，缺项已标明。
- 同类多个实例逐条列出，没有"等多处"这类模糊表述。
- 已审文件清单只包含真正通读过的文件。
- 越界线索、策略排除、无法判断的点都有记录，而不是静默丢弃。

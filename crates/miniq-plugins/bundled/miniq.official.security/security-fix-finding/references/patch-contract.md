# 补丁契约（修复模式）

本文件约束 `security-fix-finding` 修复模式下的每一次代码改动。它回答三个问题：改动之前必须弄清什么、补丁本身必须满足什么、交付时必须证明什么。

## 1. 四条基本约束

| 约束 | 含义 | 常见违例 |
| --- | --- | --- |
| 最小改动 | 只改封闭本漏洞所必需的代码与测试；不顺手重构、改格式、升级无关依赖 | 修一个注入却把整个 DAO 层换成 ORM |
| 修复根因 | 在缺失或失效的那一层控制上修，而不是在症状点打补丁 | 在一个路由里过滤 `../`，而共享的 `resolve_path()` 仍不安全 |
| 不削弱其他控制 | 不放宽鉴权、租户隔离、校验、沙箱、日志、TLS、CSP 等 | 为了让测试通过把 `verify=True` 改成 `False`，或删除失败的测试 |
| 保持兼容 | 合法输入、公共 API、错误码、默认行为不变；确需变化时显式说明 | 把所有含 `.` 的文件名都拒绝，误伤 `report.v2.pdf` |

"最小"服从"完整"：如果只有把校验下沉到共享函数才能覆盖所有入口，那么下沉就是最小方案。

## 2. 修前调查清单

在第一次 `file_edit` 之前，逐项写下答案（放进 `fix-report.md` 的"调查"一节）：

1. **攻击者输入**：谁能控制哪个值（HTTP 参数、头、文件内容、消息、环境变量、上游服务响应）？需要什么身份？
2. **源到汇路径**：以 `文件:行号` 列出从入口到危险操作的每一跳，标注中途的解析、解码、规范化、缓存、复制。
3. **被破坏的不变量**：用一句可证伪的话描述，例如"任何写入操作的目标路径解析后必须位于 `UPLOAD_ROOT` 之内"。
4. **执行边界**：这条不变量最窄的共享执行点在哪里？是否已有辅助函数只是没被调用？
5. **同类实例**：
   - 同一 sink 的所有调用者（`file_grep` 函数名）；
   - 同一危险模式的其他出现（复制粘贴的代码）；
   - 等价表示：URL 编码、双重编码、Unicode 规范化、大小写、路径分隔符、符号链接、IPv6/十进制 IP、JSON 与表单两种提交方式；
   - 其他入口：后台任务、CLI、Webhook、GraphQL 与 REST 并存、管理接口、批量接口；
   - 状态副本：缓存的权限、会话中的角色、重试/重放时复用的旧校验结果。
6. **合法行为**：列出必须继续工作的正常用例（至少一个），以及相关公共契约（文档、类型签名、错误语义）。
7. **仓库先例**：仓库里有没有已经正确处理同类问题的地方？优先模仿它。
8. **验证手段**：最小复现命令、就近测试文件、需要跑的构建/类型检查。

区分三类陈述：**事实**（有文件行号或命令输出支持）、**推断**（需说明依据）、**未决问题**（写明缺什么）。

## 3. 实施顺序

1. 写回归测试（攻击输入 + 至少一个变体 + 一个合法对照），确认在修复前失败。失败原因必须是安全断言不成立，而不是导入错误或拼写错误。
2. 在执行边界做修复。优先：仓库已有安全 API → 语言/框架标准做法 → 新增小型辅助函数。避免自写解析器、自写加密。
3. 对不安全输入显式拒绝或安全编码，不要"静默截断/替换后继续执行"——被改写后的值可能变成另一个可达的危险形式。
4. 错误信息不泄露内部路径、SQL、栈信息；拒绝时保持仓库已有的错误风格与状态码。
5. 需要时补日志（安全事件可审计），但不记录敏感值。

## 4. 补丁候选自审

修完、跑过聚焦测试后，换成攻击者视角做一次审查：

- **绕过尝试**：针对不变量构造至少三个变体输入（编码、大小写、分隔符、超长、空值、数组化参数、类型混淆、竞争条件），逐一推演或实际运行。
- **路径覆盖**：被改函数的每个直接调用方是否都经过新控制？是否有调用方绕开它直接访问底层？
- **条件两分支**：每个新增/修改的 `if` 的真假分支分别会发生什么？默认分支是否"失败即放行"？
- **校验到使用的间隙**：校验之后值是否又被修改、重新解析、重新解析符号链接（TOCTOU）？
- **误伤检查**：找一个普通或默认输入，确认它没有被新规则拒绝或改写。
- **独立审查**：可用 `agent_run` 派只读子代理，只提供 finding、仓库根、范围和 `git_diff` 输出，要求它报告有源码依据的绕过或回归并给出验证方法。只做一轮，确认后才改。

## 5. 结果契约

| outcome | 使用条件 | 对 `findings-status.json` 的影响 |
| --- | --- | --- |
| `fixed` | 回归测试修复前失败、修复后通过；原始复现不再成立；至少一个变体被阻断；合法对照与相关既有检查通过 | `status: fixed` |
| `partial` | 部分入口/变体已封闭，但仍有已知可达路径，或某项必要检查无法运行 | 保持原状态（`validated`/`plausible`），`fix_outcome: partial`，写清剩余路径 |
| `not_fixed` | 尝试修复失败：复现仍成立、测试无法通过、或修复会破坏必须保留的行为且未获同意 | 保持原状态，`fix_outcome: not_fixed` |
| `blocked` | 漏洞可能真实，但缺少环境、权限、原始上下文或产品决策，无法负责任地完成或验证 | 保持原状态，`fix_outcome: blocked`，写明缺什么 |
| `no_change` | 证据表明当前代码已安全（已被别处修复或原报告有误），未改代码 | 若确认原报告有误可建议 `rejected`，否则由用户决定；`fix_outcome: no_change` |

硬规则：任一验证步骤失败或未执行（且与本修复相关）都不得报 `fixed`；能写测试或复现时不能只靠代码阅读下结论。

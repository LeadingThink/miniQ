# 验证方法指南

本文件补充 `SKILL.md` 第 2、4 步：如何写评判标准、各技术栈如何搭最小验证环境、如何在不造成破坏的前提下拿到决定性证据。

## 一、写评判标准

好的标准满足三点：**可观察**（有明确的输出、状态或日志可看）、**与声称的影响对应**（证明的正是报告要说的后果）、**排除替代解释**（至少一条用来排除"其实是别的原因"）。

| 候选类型 | 标准示例 |
| --- | --- |
| 越权 / IDOR | ① 用户 A 的会话请求用户 B 的资源返回 200 ② 响应含 B 的数据 ③ 路由链上的授权中间件已逐一核对，均未检查归属 |
| 注入（SQL/命令/模板） | ① 载荷原样到达汇点（日志或调试断点可见）② 执行结果体现载荷语义（额外行、标记文件、计算结果）③ 换成无害等价输入时行为正常 |
| 路径穿越 / 任意文件 | ① 含 `../` 或绝对路径的输入未被规范化拒绝 ② 读取或写入了预期目录之外的**无害**标记文件 |
| SSRF | ① 服务端向攻击者指定的本地地址（本地起的监听器）发出请求 ② 能控制协议/主机/端口中的哪些部分 |
| 反序列化 | ① 不可信数据进入反序列化函数 ② 构造的对象触发了可观察副作用（创建标记文件），不使用公开利用链中的破坏性载荷 |
| 内存安全 | ① 消毒构建下复现报告的错误类型（heap-buffer-overflow 等）② 崩溃栈指向声称的函数 ③ 输入由攻击者可控接口进入 |
| 竞态 | ① 在 N 次并发尝试中出现不一致状态的次数 ② 不一致状态具有安全后果（重复扣款、越权） |
| 密码学 / 令牌 | ① 用弱点伪造或预测出一个被服务端接受的令牌 ② 或证明校验被跳过（修改签名后仍被接受） |

## 二、分技术栈的最小验证

原则：**调用真实代码**，不要把漏洞逻辑重写一遍再"证明"重写版有问题。

- **Python**：在临时副本中 `python3 -m venv .venv` 后安装依赖（先征得同意）；直接 `import` 目标模块调用函数，或用框架测试客户端（Flask `test_client`、Django `Client`、FastAPI `TestClient`）发请求，免去起服务。
- **JavaScript / TypeScript**：`node -e` 或临时测试文件 `require` 目标模块；Express/Koa 可用 `supertest`（若项目已有）；前端 XSS 在本地 dev server 上用 `browser_automation` 观察。
- **Ruby / PHP**：Rails `bin/rails runner`、`rails console`；PHP `php -r` 或 `php -S 127.0.0.1:8000` 起内置服务器。
- **Java / Kotlin**：优先写一个 JUnit 测试放在临时副本的 test 目录，用 `mvn -q -Dtest=... test` 或 `gradle test --tests ...` 只跑这一个。
- **Go**：临时 `_test.go` 文件 + `go test -run TestXxx ./pkg/...`；竞态加 `-race`。
- **Rust**：临时集成测试 + `cargo test --test xxx`；内存问题用 `cargo +nightly` 的 `-Zsanitizer=address`（若工具链可用）。
- **C / C++**：`-fsanitize=address,undefined -g -O1` 编译最小 harness，把可控输入写成文件喂给目标函数。
- **配置 / IaC**：用对应工具的"计划/渲染"模式（`terraform plan`、`helm template`、`kubectl --dry-run=client`）观察最终生效值，不对真实环境 apply。

## 三、无害证明替代表

| 声称的后果 | 用来证明的无害动作 |
| --- | --- |
| 任意命令执行 | 执行 `id` 或在验证目录写标记文件 |
| 任意文件写 | 写一个名为 `MINIQ_POC_<候选ID>` 的文件到临时副本的目标位置 |
| 任意文件读 | 读取临时副本中事先放置的标记文件，不读 `/etc/shadow`、密钥文件 |
| 数据删除 / 篡改 | 在测试数据库中对专门创建的测试记录操作 |
| 拒绝服务 | 测量单次请求的资源放大比例，不做持续压测 |
| 外连 / 数据外带 | 本地 `python3 -m http.server --bind 127.0.0.1` 监听并记录请求 |

## 四、判定与置信度

- 所有关键标准满足且证据可重放 → `validated`，confidence `high`。
- 静态追踪闭合但未运行 → 可以 `validated`，但 confidence 最高 `medium`，并在 `proof_gaps` 写明"未动态复现"。
- 有决定性反证（控制确实生效、路径不可达、输入被类型系统限制）→ `rejected`，反证写入 `counterevidence`，引用具体文件行。
- 其他情况 → 保持 `open`，写清证据缺口。不要为了"有结论"而强行判定。

## 五、常见误判

- 在测试里手工关掉了本来生效的中间件，然后"证明"越权——这证明的是测试写法，不是漏洞。
- 用管理员账号复现"越权"——应当用最低权限的攻击者身份。
- 只证明输入到达了汇点，没证明汇点能被利用（例如参数化查询里的字符串到达了 SQL 层，但并不构成注入）。
- 在开发模式下复现的问题，生产配置默认关闭（例如调试端点）——需在 `preconditions` 注明，交由 `security-attack-path` 调整 likelihood。

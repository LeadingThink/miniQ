# 安全策略（SECURITY.md）起草与审阅

目标：产出一份对维护者、报告者和后续安全扫描都有用的安全策略——它回答"这个系统保护什么、信任什么、什么算漏洞、什么不算、怎么报告"。它既是对外的漏洞披露政策，也是 `security-scan`、`security-triage-finding` 判断范围与严重度的依据。

## 触发场景

- "帮我写个 SECURITY.md""审一下我们的安全策略""版本变了，安全策略要不要更新""明确一下哪些问题不算漏洞"。
- 扫描或分诊时发现缺少策略，导致范围争议反复出现。
- 仓库有多个组件（插件、SDK、服务、CLI）需要各自的范围说明。

不适用 / 应转交：

- 找漏洞 → `security-scan` / `security-review`；分析架构与攻击场景 → `security-threat-model`（其产出可作为本技能输入）。
- 判断某份报告是否在范围内 → `security-triage-finding`（它读取本技能产出的策略）。
- 加固措施设计 → `security-hardening`。
- 法律条款（安全港、赏金金额、合规承诺）：本技能只起草占位，须由用户或法务确认。

## 前置条件

- 可读仓库；写入 `SECURITY.md` 前必须通过 `ask_user` 取得明确同意（预览 → 同意 → 写入）。
- 策略中的每项技术断言都要能在代码或文档中找到依据；找不到的标为"待确认"并询问用户，不编造。
- 联系方式、响应时限、支持版本等运营信息只能来自用户或现有文档。

## 分步流程

1. **定位已有策略**（`file_glob`、`file_read`）：按 `references/security-md-structure.md` 第 1 节的查找顺序搜索 `SECURITY.md`、`.github/SECURITY.md`、`docs/SECURITY.md`、组件目录下的策略，以及 `CONTRIBUTING.md`、README 的安全章节、已有威胁模型（`docs/security/threat-model.md`）。确定模式：新建 / 审阅 / 更新；多个文件时确定各自适用范围与优先级。
2. **确定目标与读者**（`ask_user`）：一次性确认：策略覆盖范围（整仓还是某组件）、项目类型（库、服务、CLI、桌面应用、插件平台）、是否开源/有漏洞赏金、联系渠道、支持版本、期望响应时间。用户不确定的项保留占位。
3. **建立系统边界**（`file_glob`、`file_read`、`file_grep`；大仓库可用 `agent_run` 并行）：
   - 找出组件、入口（网络接口、CLI、IPC、插件接口、文件解析）、部署形态与默认配置。
   - 识别信任边界：哪些输入来自不可信方，哪些调用方被信任（管理员、本机用户、插件作者、配置文件）。
   - 识别已存在的安全机制：认证、沙箱、权限确认、隔离、加密、审批流程。
   - 已有威胁模型时直接复用其资产、边界、假设，避免重复分析。
   - 大仓库：用 `agent_run`（`runInBackground=true`）按组件分派"边界事实收集"子任务，要求返回 `path:line` 证据，用 `process_output` 收集。
4. **提炼安全不变量**（本地推理 + `file_read` 核对）：写成可检验的陈述，如"未经用户确认，插件不能执行 shell 命令""A 租户的数据不能被 B 租户读取"。每条附依据位置或标注"期望，尚未由代码保证"。
5. **划定可报告与不受理范围**：依据不变量推出"违反即为漏洞"的类别；列出明确不受理的（需要已被信任的能力、物理访问、社会工程、第三方依赖自身问题、仅影响自身的行为、已声明的接受风险），每项说明理由；列出已知限制及补偿控制。严重度语境：说明什么样的影响在本系统里算严重。
6. **起草或修订**（本地）：按 `references/security-md-structure.md` 的章节结构写草稿；更新模式下只改有变化的章节，保留用户原有措辞和运营信息。
7. **自审**（`file_read`、`file_grep`）：按 `references/review-checklist.md` 逐项检查，尤其是"与代码一致"：每条关于机制、默认值、配置项、命令、路径的断言都实际检索一次。
8. **预览并征求同意**（`ask_user`）：展示完整草稿（更新模式展示差异要点与新全文），列出待确认项与假设，询问写入位置。未获同意不写入。
9. **写入与核对**（`file_write` 或 `file_edit`、`git_diff`）：写入后用 `git_diff` 展示变化；若 README/CONTRIBUTING 需要加指向链接，单独征求同意。不提交 git。

## 工具与参数要点

- 查找：`file_glob` 模式 `**/SECURITY.md`、`**/security.md`、`**/SECURITY*.md`、`**/.github/SECURITY.md`；排除 `node_modules`、`vendor`、第三方目录。
- 核对断言：`file_grep` 搜配置项名、命令名、默认值；`file_read` 读实现确认行为而不是只看注释。
- 版本信息：`shell_run` 执行 `git tag --sort=-creatordate | head` 了解版本线，用于"支持版本"表的建议（最终以用户确认为准）。
- 引用外部标准（CVSS、CWE、RFC 9116 `security.txt`）时可用 `web_search`/`web_fetch` 核对，但不照搬外部策略文本。

## 质量检查

- 每条不变量、机制断言都有 `path:line` 依据或"待确认"标记；没有虚构的联系方式、时限或赏金。
- 不受理范围不是笼统的"不在范围内"，而是有理由、不会误伤真实漏洞（例如"需要管理员权限"不能排除"普通用户可提权为管理员"）。
- 可报告与不受理的边界清晰且不冲突；与已有威胁模型一致。
- 组件级策略与根策略的关系写清楚（覆盖/补充）。
- 读者视角：外部报告者读完能判断"我这个问题该不该报、怎么报"。

## 失败回退

- 用户无法提供联系方式/时限：保留明显的占位（如 `<安全联系邮箱>`），在交付中列为必须补充项，不写入虚假值。
- 仓库太大无法完整梳理：先覆盖主要入口与信任边界，在策略"已知限制"或交付说明中注明未覆盖的组件，并建议先运行 `security-threat-model`。
- 用户不同意写入：只交付草稿文本与审阅意见。
- 发现与策略冲突的实际漏洞：不写进公开策略，单独告知用户并建议 `security-triage-finding` / `security-fix-finding`。

## 交付格式

1. 模式与范围：新建/审阅/更新，适用的文件与组件。
2. 草稿全文（或更新后的全文 + 变更要点）。
3. 依据表：`断言 | 依据 path:line | 状态（已核实/待确认）`。
4. 审阅意见（审阅模式）：按 `references/review-checklist.md` 的分组列出问题与建议，按重要性排序。
5. 待用户确认事项与写入结果（路径、`git_diff` 摘要）。

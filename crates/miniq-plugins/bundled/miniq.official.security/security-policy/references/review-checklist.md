# SECURITY.md 审阅清单

审阅时逐项标注：✅ 满足 / ⚠️ 部分满足 / ❌ 缺失 / N/A。每个 ⚠️ 与 ❌ 都要给出具体修改建议（最好附替换文本）和优先级（高：影响报告判断或存在误导；中：影响可用性；低：措辞与格式）。

## A. 定位与层级
- [ ] 文件位于托管平台可识别的位置（根、`.github/`、`docs/`），或从 README 可找到。
- [ ] 多份策略并存时，写明各自适用的组件与优先关系，且互不矛盾。
- [ ] 组件级策略没有放宽根策略的安全保证。

## B. 系统与范围
- [ ] 说明了系统是什么、部署形态、主要用户。
- [ ] 列出在范围内与不在范围内的组件/仓库/渠道。
- [ ] 支持版本表存在且与实际发布线一致（用 `git tag` 或发布记录核对）。

## C. 威胁模型与信任边界
- [ ] 列出受保护资产。
- [ ] 列出参与方及信任级别，特别是容易误解的（插件作者、本机其他用户、模型输出、配置文件）。
- [ ] 指明不可信输入的入口。
- [ ] 与仓库内已有威胁模型一致。

## D. 安全不变量
- [ ] 以可检验的陈述表达，而非口号（"我们重视安全"不算）。
- [ ] 每条都能在代码中找到实现依据（`file_grep`/`file_read` 核对，记录 `path:line`）。
- [ ] 未实现或部分实现的内容已移入"已知限制"。
- [ ] 覆盖主要攻击面：认证/授权、隔离/沙箱、数据保护、更新与分发完整性、默认配置。

## E. 可报告问题与严重度
- [ ] 可报告类别与不变量对应。
- [ ] 给出严重度语境或采用的评分方法。
- [ ] 说明报告应包含的信息。

## F. 不受理范围与接受风险
- [ ] 每一项都有理由。
- [ ] 措辞不会误伤真实漏洞（尤其是"需要认证""需要本地访问""需要用户交互"这类笼统排除）。
- [ ] 接受风险写明理由与复审时机。
- [ ] 第三方依赖问题的处理方式清晰（上游报告 vs 本项目使用方式引入的问题）。

## G. 已知限制与补偿控制
- [ ] 列出已知限制及用户可采取的补偿措施。
- [ ] 绕过补偿控制是否可报告有明确说明。

## H. 报告与响应
- [ ] 提供私密报告渠道，并明确不要使用公开 issue。
- [ ] 联系方式真实有效（由用户确认，不由审阅者猜测）。
- [ ] 响应时限、披露流程、致谢/CVE/赏金说明明确且可兑现。
- [ ] 安全港/法律声明（如有）由用户或法务确认。

## I. 与代码一致性（重点）
对策略中的每条技术断言执行：
1. 提取断言中的机制名、配置项、默认值、命令、路径。
2. `file_grep` 搜索实现与默认值；`file_read` 阅读实现逻辑（不只看注释或文档）。
3. 记录到依据表：`断言 | 依据 path:line | 结论（一致/不一致/找不到）`。
4. 不一致时：以代码为准修改策略，或把期望写入"已知限制"；如果不一致构成真实漏洞，单独告知用户，不写入公开策略。

常见不一致：声称默认开启但实际默认关闭；声称有权限确认但某条路径绕过；支持版本表过期；提到的配置项已改名；联系邮箱与其他文档不同。

## J. 可读性
- [ ] 外部报告者能在 1 分钟内找到报告方式。
- [ ] 语言清晰，无内部术语或未解释的缩写。
- [ ] 有最后更新日期。

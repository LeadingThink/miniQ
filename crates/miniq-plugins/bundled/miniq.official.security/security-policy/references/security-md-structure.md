# SECURITY.md 结构指南

一份好的安全策略同时服务三类读者：**外部报告者**（这个问题该不该报、怎么报）、**维护者**（收到报告如何判断范围与严重度）、**自动化安全流程**（`security-scan`、`security-triage-finding` 以它约束范围）。因此它不只是"联系邮箱"，还要写清系统边界与安全承诺。

## 1. 查找顺序与适用范围

扫描、分诊、建模时按以下顺序寻找适用的策略，**越靠近被分析代码的越优先**，上层策略作为补充：

1. 被分析文件所在组件目录向上逐级查找 `SECURITY.md` / `security.md`（如 `packages/foo/SECURITY.md`、`crates/bar/SECURITY.md`），直到仓库根。
2. 仓库根 `SECURITY.md`。
3. `.github/SECURITY.md`（托管平台展示位置）。
4. `docs/SECURITY.md`、`docs/security/*.md`（含威胁模型 `docs/security/threat-model.md`）。
5. `CONTRIBUTING.md`、`README*` 中的"安全/Security"章节。
6. 组织级默认策略（如托管平台组织的 `.github` 仓库）——仓库内不可见时只作提示。

多份并存时：组件级策略可**收窄或补充**根策略的范围，但不应放宽根策略中的安全不变量；冲突时在交付中指出，请用户裁定。

## 2. 推荐章节

以下章节顺序可调整，但内容应齐全。小项目可合并章节，每节 2–5 行即可。

### 2.1 系统与范围
- 一两句话说明系统是什么、谁在用、怎么部署（本地工具、托管服务、库、插件平台）。
- **在范围内**的仓库/组件/发布渠道；**不在范围内**的（示例代码、实验目录、第三方 fork、演示站点）。
- 支持版本表：`版本 | 是否接收安全修复`。只写用户确认过的内容。

### 2.2 威胁模型与信任边界
- 资产：系统保护什么（用户数据、凭据、宿主机、其他租户、签名密钥、账单）。
- 参与方与信任级别：匿名用户、登录用户、管理员、本机用户、插件/扩展作者、上游服务、配置文件作者。
- 信任边界：不可信数据从哪里进入（网络请求、打开的文件、网页内容、模型输出、插件、IPC），哪些被视为可信（本机管理员配置、签名的更新包）。
- 可引用完整威胁模型文件，此处只放摘要。

### 2.3 安全不变量
- 以"系统保证……"的可检验陈述列出，每条对应一种可被违反的承诺，例如：
  - 未经用户逐次确认，扩展不能执行宿主命令或写工作区外文件。
  - 一个租户不能读取或修改另一租户的数据。
  - 默认配置下服务不会监听非回环地址。
- 这是判断"是否是漏洞"的核心依据：**违反任一不变量即为可报告的安全问题**。
- 不变量应与代码一致；期望但尚未实现的写到"已知限制"。

### 2.4 可报告的问题与严重度语境
- 列出典型可报告类别，最好与不变量对应（越权、沙箱逃逸、远程代码执行、凭据泄露、跨租户访问、签名绕过……）。
- 严重度语境：在本系统中什么影响算严重/高/中/低，例如"不需要用户交互即可在宿主执行代码"为严重，"需要用户打开特制文件"降一级。可声明使用 CVSS 或自定义矩阵。
- 报告最好包含的信息：受影响版本、复现步骤、影响、概念验证（不要求攻击真实用户）。

### 2.5 不受理范围、例外与接受风险
- 每一条都写理由，理由通常属于以下几类：
  - 需要攻击者已拥有同等或更高权限（例如已能修改本机配置文件、已是管理员）。
  - 需要物理访问、已被攻陷的设备、社会工程。
  - 第三方依赖或平台本身的问题（请报告给上游），除非本项目的使用方式引入了问题。
  - 只影响攻击者自己的行为（自我 XSS、自身账号 DoS）。
  - 缺少最佳实践但无可演示的影响（缺少某响应头、版本号暴露）。
  - 设计上明确的行为与**已接受风险**（写明为何接受、何时复审）。
- 注意措辞精确：排除"需要管理员权限的操作"，不等于排除"普通用户获得管理员权限"。

### 2.6 已知限制与补偿控制
- 目前未防护或只部分防护的场景，及用户可采取的补偿措施（例如"不要在不可信目录运行""为插件启用审批模式"）。
- 这些不应作为新漏洞重复报告，但绕过补偿控制本身可能是可报告的。

### 2.7 如何报告与响应流程
- 私密渠道：安全邮箱、托管平台的私密漏洞报告、表单；可提供加密公钥指纹。明确要求**不要**公开 issue。
- 响应时限：确认收到、初步评估、修复/披露目标（只写团队能兑现的）。
- 披露政策：协调披露周期、致谢方式、CVE 申请、是否有赏金。
- 安全港声明（如有）：由用户或法务提供，本技能只保留占位。

### 2.8 元信息
- 最后更新日期、适用版本/提交、维护者；变更记录（可选）。

## 3. 与其他文档的关系
- 威胁模型（`security-threat-model` 产出）：提供 2.2 与 2.3 的依据；策略放摘要，模型放细节。
- `security.txt`（RFC 9116）：面向网站的联系方式，可指向 SECURITY.md。
- README/CONTRIBUTING：放一行链接即可，避免多处维护不一致。

## 4. 骨架（起草时按项目实际填写，不要保留空话）

```markdown
# 安全策略

## 范围
<系统简述；在范围内的组件与发布渠道；不在范围内的内容>

| 版本 | 安全修复 |
| --- | --- |
| <版本> | <是/否> |

## 威胁模型摘要
- 保护的资产：…
- 信任的参与方：…
- 不可信输入：…
（完整模型见 <路径>）

## 安全保证
1. <不变量 1>
2. <不变量 2>

## 可报告的问题
- <类别>：<说明，对应的保证编号>
严重度参考：…

## 不受理的问题
- <类别>：<理由>

## 已知限制
- <限制>：<补偿措施>

## 报告方式
<私密渠道>；请勿公开提交 issue。
我们将在 <时限> 内确认收到……

最后更新：<日期>
```

## 5. 常见缺陷

| 缺陷 | 后果 | 改进 |
| --- | --- | --- |
| 只有联系邮箱 | 报告者无法判断范围，维护者被低质量报告淹没 | 补充范围、不变量、不受理项 |
| 不受理项过宽（"所有需要认证的问题"） | 真实越权漏洞被拒 | 按"攻击者新增能力"描述 |
| 描述与代码不符（声称有沙箱但默认关闭） | 误导用户，削弱信任 | 以代码为准，限制写入"已知限制" |
| 承诺无法兑现的时限 | 失信 | 只写实际能力 |
| 公开 issue 作为报告渠道 | 漏洞提前公开 | 私密渠道 |
| 多份策略互相矛盾 | 分诊争议 | 明确层级与覆盖关系 |

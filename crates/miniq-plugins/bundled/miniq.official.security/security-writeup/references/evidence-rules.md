# 证据规则

漏洞报告最常见的失败不是写得不好，而是把“我以为”写成了“我观察到”。本文件规定证据的分类、标注、盘点、版本追溯与测试授权。

## 1. 六类证据

| 类别 | 定义 | 正文写法 |
| --- | --- | --- |
| 源码证据 | 在锁定版本中亲自读到的代码、配置、构建脚本 | 直接陈述，附路径与摘录：“`export_order` 只检查登录状态。” |
| 实际运行观察 | 在授权环境里真正执行并看到的输出、日志、响应 | 写明环境与动作：“在 2.5.1 容器中以 mallory 请求后收到 200 与 alice 的订单。” |
| 未执行 PoC | 写好或收到但没有运行的脚本/请求 | “以下 PoC 未执行；预期输出（未观察）…” |
| 报告声明 | 报告人、工单、扫描器的说法，我们未独立核实 | “报告人称……，我们未能独立确认。” |
| 推断 | 基于已知事实的合理推理 | 明确标记：“推断：由于批量导出复用同一函数，它很可能同样受影响（未验证）。” |
| 未知 | 没有证据可判断的事项 | “未知：实际部署中有多少实例开启了该选项。” |

规则：

- 证据类别只能向上升级靠行动：要把“报告声明”或“推断”写成直接陈述，就先去读源码或运行验证。
- **绝不伪造**：命令输出、崩溃栈、响应体、截图、耗时、CVE/GHSA 编号、CVSS 向量、修复版本号、披露日期。需要展示预期效果时明确写“预期（未观察）”。
- 汇总性结论（执行摘要、严重度）取决于链条中最弱的一环：只要关键一环是推断，总结论就是有条件的。
- 源码与声明矛盾时，源码优先；把矛盾写出来，而不是巧妙绕开。
- 报告人的 PoC 即使看起来合理，在我们跑过之前仍然是“未执行 PoC”。

## 2. 证据盘点表

起草前先填写（可在草稿目录内存为 `evidence.md`，交付时可合入附录）：

| 项目 | 内容 | 证据类别 | 来源 |
| --- | --- | --- | --- |
| 原始声明 | 报告人/扫描器怎么说 | 报告声明 | 工单号或文件 |
| 源码版本 | 发布号 + 提交 + 工作区是否干净 | 源码证据 | `git describe` 输出 |
| 入口 | 路由/命令/接口及其路径 | | |
| 应有的控制 | 预期的校验/授权 | | |
| 失效点 | 控制为何没生效 | | |
| 汇点与后果 | | | |
| 角色与权限 | Alice/Bob/Mallory 各自是谁 | | |
| 配置条件 | 默认/可选/未知 | | |
| PoC 状态 | 已执行/未执行/来自报告人 | | |
| 运行记录 | 日志/输出文件路径 | 实际运行观察 | |
| 引入提交 / 受影响版本 | 见第 3 节 | | |
| 已有修复 | 补丁、修复版本、回港分支 | | |
| 测试授权 | 授权范围与授权人 | — | 对话记录 |
| 尚未解决的未知项 | | 未知 | |

表里写“未知”没有问题；空格才是问题。

## 3. 版本追溯

目标是回答三个问题：哪个变更引入了问题、哪些发布包含了可达的问题、哪个发布首次修复。步骤（均用 `shell_run`）：

1. **确认历史完整**：`git rev-parse --is-shallow-repository`；为 `true` 且已获授权时 `git fetch --unshallow --tags`。`git tag --list | wc -l` 确认有 tag。
2. **找引入变更**（按需组合）：
   - `git log -L <起>,<止>:<path> --oneline` —— 看出问题的几行如何演变；
   - `git log -S'<关键表达式>' --oneline -- <path>` —— 找某段代码首次出现/消失；
   - `git blame -w -C -L <起>,<止> <path>` —— 定位最近改动，注意格式化提交会掩盖真正来源；
   - `git log --follow -- <path>` —— 文件重命名后继续追。
   注意：漏洞常常在“删掉了一个校验”或“新增了一个绕开校验的入口”时引入，汇点所在行可能很早就存在。
3. **候选发布**：`git tag --contains <引入提交> --sort=v:refname`。注意预发布 tag（`-rc`、`-beta`）与多条维护线。
4. **逐点确认**：至少检查——引入前最后一个发布、首个受影响发布、每条维护线的最新发布、首个修复发布。用 `git show <tag>:<path>` 阅读对应代码，确认入口存在、控制确实缺失、没有别处补偿性防护。含有引入提交但入口尚未暴露或功能未启用的版本，不算受影响。
5. **修复与回港**：`git log --oneline <引入提交>..HEAD -- <path>` 找可能的修复，`git tag --contains <修复提交>`、`git branch -r --contains <修复提交>` 确认覆盖的发布与分支。cherry-pick 的回港提交哈希不同，需按内容（`git log -S`）查找。
6. **中间版本**：没有逐一检查的就写“抽查”，不要默认全部受影响。
7. **依赖类漏洞**：受影响范围以我们发布中锁定的依赖版本为准（逐个 tag 查看锁文件），不是上游公告的范围。

输出为 `report-format.md` 第 7 节的表格。

## 4. 测试授权与运行安全

- 只在用户明确授权的环境运行：本机容器、临时目录、用户指定的测试实例。授权需要针对具体目标；“可以测试”不等于可以打生产。
- 不对公网服务、生产系统、共享预发环境、第三方 SaaS 发送攻击请求。需要这样做才能证明时，停下来 `ask_user`。
- 破坏性、崩溃、资源耗尽类 PoC 只在隔离容器内运行，并限制时间与资源；不得影响其他用户。
- 使用假数据与示例账号（alice/bob/mallory），不读取、不保存真实用户数据。
- 保存原始输出到报告目录的 `poc/output/`（或仅在正文引用关键行），并记录命令、环境、时间。
- 运行结束按 PoC 的清理步骤关闭容器、删除临时数据。

## 5. 角色命名

| 名字 | 身份 | 何时出现 |
| --- | --- | --- |
| Alice | 合法用户、资源所有者、受害者 | 几乎总是 |
| Bob | 第二名合法用户或预期接收者 | 需要区分两个合法方时 |
| Mallory | 主动攻击者 | 几乎总是 |
| Eve | 被动窃听者 | 仅网络拦截类问题 |
| Trent | 可信第三方（身份提供商、CA） | 仅涉及信任中介时 |

角色的权限必须与产品实际一致；同一份报告内角色含义不得漂移。不要引入没有作用的角色。

## 6. 可移植性

- 路径写仓库相对路径（`src/orders/export.py`），命令写报告目录相对路径（`poc/run.sh`）。
- 不得出现作者机器信息：用户名、家目录、临时目录、主机名、内网 IP。目标系统上复现必需的绝对路径（如容器内 `/etc/app/config.yml`）除外。
- 内部工单链接、内部平台名称在对外版本中移除或泛化。
- 凭证、令牌、Cookie 用明显的假值（`mallory-session-token`），真实值一律打码。

## 7. 常见退回原因

- 把报告人的影响描述原样当成结论。
- “受影响版本：所有版本”但只检查了 HEAD。
- PoC 输出看起来太干净、没有运行记录。
- 为证明漏洞假设了攻击者已有管理员权限，或悄悄换成了另一个更弱的目标。
- 修复建议只封住了 PoC 的具体载荷，没有修根因。
- 正文出现 `/Users/...`、`C:\...` 或 `TODO`。

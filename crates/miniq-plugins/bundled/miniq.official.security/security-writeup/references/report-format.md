# 单漏洞报告格式

本文件规定 `security-writeup` 产出报告的章节、每节应回答的问题和写法。起草子代理在动笔前必须读完本文件和 `evidence-rules.md`。章节顺序固定，标题可按用户语言书写（默认中文）。某节确实无内容时保留标题并写一句原因（如“尚无修复”），不要删节，也不要用空话填充。

## 0. 文件头

报告首行是一级标题（即报告标题），紧接一个元信息表：

```markdown
# 订单导出接口缺少归属校验，普通用户可下载他人订单

| 项 | 内容 |
| --- | --- |
| 产品 / 组件 | shop-server / 订单导出 |
| 评估版本 | 2.5.1（工作区干净） |
| 严重度 | 高（impact 高 × likelihood 高） |
| 类别 | 不安全的直接对象引用（CWE-639） |
| 受影响版本 | 2.3.0 – 2.5.1（已逐一检查 2.3.0、2.4.0、2.5.1） |
| 修复版本 | 尚未发布 |
| 证据等级 | 已在本地容器复现 |
| 报告状态 | 草稿 / 待上游确认 |
```

“证据等级”只能取：`已复现`（有实际运行观察）/`源码闭合（未运行）`/`仅基于报告材料`。没有 CVE/GHSA 编号就不写该行，绝不占位。

标题写法：“哪里 + 缺了什么 + 谁能得到什么”。不要只写“IDOR 漏洞”，也不要夸张成“完全接管”。

## 1. 执行摘要

面向没有上下文的决策者，3–6 句：

- 谁（Mallory 的身份与前置权限）能对什么（资源/组件）做什么（后果）。
- 受影响的发布版本与所需配置（默认 / 可选 / 未知）。
- 证据等级：是否实际复现。
- 建议的处置与紧迫程度。

写法示例：“在 2.3.0 至 2.5.1 中，任何已注册用户只要把导出链接里的订单号换成别人的，就能下载对方完整的订单（含收货地址与电话）。我们在本地容器中复现了这一点。该行为在默认配置下存在。建议尽快在服务层补上归属校验。”

摘要里不出现提交哈希、行号或术语堆砌。

## 2. 背景

让读者理解“正常应该怎样”：

- 组件是做什么的，谁会调用它，数据从哪里来。
- 引入本报告会用到的人物，只引入需要的：Alice（合法的资源所有者）、Bob（另一名合法用户或预期接收者）、Mallory（主动攻击者）、Eve（被动窃听者，仅在涉及拦截时）。示例用户名统一用 `alice`、`bob`、`mallory`、`eve`。
- 写明每个人的真实账号类型与权限；不要让“普通用户 Mallory”拥有产品实际不给普通用户的权限。
- 说明相关的安全边界（租户隔离、账号隔离、沙箱、信任的上游服务等）。

必要的术语只定义一次。

## 3. 漏洞细节

按因果顺序讲述：入口 → 数据如何传递 → 应有的控制 → 哪里失效 → 到达的汇点。

- 开头用一句话说清“应该怎样 / 实际怎样”。例：“只有 Alice 应能读取她的订单，但导出处理函数只检查 Mallory 是否登录，没有检查订单属于谁。”
- 每一步配最短的决定性源码摘录，摘录前写明 `仓库相对路径` 与函数名、所属发布版本；摘录后用一两句话解释“这段代码改变了什么结果”以及“它没有回答的问题”。
- 跨组件问题：先展示各组件单独的正常防护，再展示共享的状态/键，最后展示接收方的错误决策。
- 只在对象生命周期、事件序列确实复杂时才加状态表或时序图。
- 根因：缺的是哪一层的哪个控制；若历史有助于理解（如重构时丢失了校验），简述引入变更的意图。

摘录格式：

````markdown
`src/orders/export.py` 中的 `export_order`（2.5.1）：

```python
@login_required
def export_order(request, order_id):
    order = Order.objects.get(id=order_id)
```

这里只有登录校验，查询条件中没有任何与当前用户相关的限制。它尚不能说明上游中间件是否已按归属过滤——这一点在下一段确认。
````

## 4. 可利用性分析

- 前置条件清单：账号类型、网络位置、配置项（标明默认/可选/未知）、需要知道的信息（如订单号是否可枚举）。
- 攻击者实际获得的能力（原语）与报告声称的影响对比，取较窄的一个；更强的影响只能写成“可能”并说明还缺什么。
- 已检查过的防护与死胡同：哪些检查会中断攻击、为什么在这里不生效。
- 可靠性：确定性触发还是依赖时序/内存布局；“可能的交错”不等于“生产环境可靠利用”。
- 部署普遍性：没有实测数据就写“未知”。
- 严重度：写出 impact 与 likelihood 各自的理由；如需 CVSS，每个指标一句依据，无法确定的指标不要硬填。

## 5. 概念验证（PoC）

先写状态行，三选一：

- **已执行**：写明环境（容器镜像、软件版本、配置）、时间、执行者。
- **未执行**：说明原因（无授权环境、需要硬件等）。
- **来自报告人，已阅读未运行**。

然后是：

1. 环境准备（用报告相对路径命令，如 `docker compose -f poc/compose.yml up -d`）。
2. 逐步操作：先以 `alice` 创建资源，再以 `mallory` 执行攻击。请求写完整（方法、路径、关键头、请求体），凭证用明显的示例值。
3. **观察到的输出**：仅在确实运行过时粘贴，原样保留关键行，可删节但标注 `…（省略）…`。未运行时标题改为“预期输出（未观察）”。
4. 阴性对照：例如 `bob` 访问不存在的订单返回 404、打补丁后 `mallory` 收到 403。没做就明说“未执行阴性对照”。
5. 清理步骤。

所有 PoC 代码、脚本、输出中不得含作者机器的绝对路径、真实凭证、真实用户数据。

## 6. 修复建议

- 用大白话说明代码应该改成什么行为，再给最小补丁思路（可附 diff 片段，标明“建议补丁，未合入上游”）。
- 修复应放在哪一层（统一入口而非单点补漏），是否有同模式的兄弟路径需要一起修。
- 建议的回归测试：正向（Alice 仍可用）与反向（Mallory 被拒）。
- 临时缓解措施（WAF 规则、关闭功能开关）及其局限。
- 已有上游修复时：确认它修的是同一行为并确实阻止本报告的攻击后再引用，写明修复版本与回港分支。

## 7. 受影响版本

用表格区分“已确认”和“推断/未检查”：

| 版本 / 分支 | 状态 | 依据 |
| --- | --- | --- |
| 2.2.x | 不受影响（已检查 2.2.4） | 旧实现在查询中带 `owner=request.user` |
| 2.3.0 | 受影响（已检查） | 引入变更：导出功能重构，改用通用 `get` |
| 2.3.1 – 2.4.x | 受影响（抽查 2.4.0） | 中间补丁版未逐一检查 |
| 2.5.1 | 受影响（已检查，已复现） | 评估版本 |
| main | 受影响 | 截至报告日未修复 |

表后用一句话总结，并说明历史或 tag 的缺失（如“2.0 之前的历史不在公开仓库中，更早版本未知”）。只有引入/修复提交对理解有帮助时才给出短哈希。

## 8. 时间线

按日期列出已发生的事件：发现/收到报告、确认、通知上游、上游回复、修复合入、发布、公开披露。只写有记录的事件；计划中的事件标注“计划”。不要补造日期。

```markdown
| 日期 | 事件 |
| --- | --- |
| 2025-02-27 | 收到外部研究者报告 |
| 2025-03-02 | 完成分诊并在本地复现 |
| 计划 2025-03-30 | 预计公开披露（视修复进度） |
```

## 9. 附录（可选）

- 证据清单：每条关键断言对应的证据类别（见 `evidence-rules.md`）。
- 未解决问题与后续工作。
- 参考资料：已确认存在的链接（发布说明、相关 CWE）。

## 文风

- 像一位认真的研究者在向同行讲解：直接、准确、温和。用“我们”带读者走推理；“我”只用于确实执行过的操作（“我在 2.5.1 容器中运行了…”）。
- 把证据说成具体的东西：“显示 Mallory 拿到 Alice 订单的那次响应”“缺少归属条件的那几行查询”，而不是“证据 A”这类抽象标签。
- 不写营销腔、不堆理论、不加为了显得严重的变体。简单问题就写得简单。
- 正文以发布版本号为主；不要在每段摘录后附提交哈希。
- 所有路径为仓库相对路径，所有命令为报告目录相对路径。

## 验收清单（主代理对每份草稿）

- [ ] 章节 0–8 齐全、顺序正确；元信息表无占位内容。
- [ ] 一句话攻击陈述与正文、PoC 中的触发序列一致。
- [ ] 每段摘录已对照指定版本核实。
- [ ] 受影响版本表中每一行都有依据。
- [ ] 观察输出确有运行记录；预期输出标注未观察。
- [ ] 无作者机器绝对路径、无真实凭证。
- [ ] 角色名使用正确且前后一致。

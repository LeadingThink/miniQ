# KPI 设计

## 触发场景
- “我们该看哪些指标”“帮我设计增长团队的 KPI”“给这个新功能定个成功指标”
- 制定 OKR/年度目标，需要基线与目标值
- 现有指标太多、互相矛盾、被“刷”，需要重构

## 前置条件
- 知道要服务的决策或目标（业务目标、团队职责、时间周期）
- 最好有历史数据用于确定基线与可行目标；没有时基于基准与假设设定，并标注
- 框架与定义模板见 `references/kpi-framework.md`；目标设定方法见 `references/target-setting.md`

## 分步流程
1. **明确决策**：用 `ask_user`（如未说明）确认：谁用这些指标、用来做什么决策、复盘频率、业务阶段（探索/增长/成熟）。
2. **收集证据**：
   - 业务背景与现有定义：`data-business-context`、`data-context-layer`
   - 数据可得性：`file_glob`/`doc_read`/`shell_run` 查询可用字段与历史长度
   - 若数据可疑，先做 `data-quality-audit`
3. **构建候选集**：从价值链出发（获客 → 激活 → 使用 → 留存 → 变现 → 推荐，或 投入 → 过程 → 产出 → 成果），每层列 2–4 个候选，包含领先与滞后指标。
4. **评估与选择**：用 `references/kpi-framework.md` 的评分维度（与目标相关、可被团队影响、可度量、及时、难以被刷、易懂）打分；确定：
   - 1 个北极星/主指标
   - 3–5 个驱动指标（可行动、领先）
   - 2–3 个护栏指标（防止以损害其他目标为代价达成主指标，如质量、成本、体验）
5. **写清定义**：每个指标一张定义卡（名称、目的、公式、分子分母、粒度、过滤、时间窗、数据源、刷新频率、负责人、好的方向、已知局限）。
6. **历史检验**：有数据时，`file_write` 写 `analysis/kpi/backtest.py` 计算历史值，检查：波动幅度、与主指标的相关性与领先性、各分群是否表现一致、是否对口径细节敏感。
7. **设定目标**：按 `references/target-setting.md`（基线 + 历史增长、同类基准、自下而上拆解、分层目标“保底/目标/挑战”），给出依据。
8. **交付**：`analysis/kpi/kpi-design.md`；如需看板骨架，可直接生成 `data-dashboard` 的 JSON 规格草稿；需要定期报告时衔接 `data-kpi-reporting`。

## 工具与参数要点

- `file_read`/`doc_read`：读取业务目标、OKR 和已有指标文档（`data-context/metrics.md`）
- `shell_run`：用历史数据计算基线、波动和季节性，用于设定目标区间。可复用 `<插件目录>/data-kpi-reporting/scripts/kpi_scorecard.py <定义.json> --period <期间>` 试算
- `file_write`：输出 `analysis/kpi/kpi-design.md` 和可供记分卡直接使用的定义 JSON（`analysis/kpi/definitions.json`，字段与 kpi_scorecard 的 definitions 一致）
- `web_search`：查行业基准，作为目标设定的参考，并注明来源和适用范围
- `ask_user`：决策归属、目标的激进程度、北极星指标取舍需要用户拍板
- 每个 KPI 都必须写全：口径（分子/分母）、粒度、更新频率、负责人、好方向、阈值

## 质量检查
- 指标总数克制（一般 ≤ 8 个核心）；每个都有明确负责人与行动含义
- 每个比率指标写清分母；每个指标写清“向上/向下为好”
- 驱动指标与主指标的关系有逻辑或数据支持
- 至少一个护栏指标覆盖质量/体验/成本
- 目标值有依据，且说明不确定性

## 失败回退
- 没有历史数据：用行业基准或试运行期数据确定初始目标，并约定 N 周后复核
- 利益相关方意见冲突：列出选项与取舍，用 `ask_user` 请决策人选择
- 指标无法计算（缺埋点）：给出所需埋点/字段清单与替代代理指标

## 交付格式
`analysis/kpi/kpi-design.md`：
1. 目标与决策背景
2. 指标树（北极星 → 驱动 → 护栏），可用 Mermaid 或缩进列表
3. 指标定义卡
4. 候选指标评估表（含淘汰原因）
5. 基线与目标（保底/目标/挑战）及依据
6. 数据缺口与埋点需求
7. 复盘节奏与负责人

# 业务上下文检索

分析之前或之中，找到“解释数字所必需的背景”，并且只取对当前决策有用的部分。

## 触发场景
- “上个月为什么掉了？当时有什么活动/发版吗？”
- 需要指标的官方定义、目标、负责人
- 需要历史分析结论、行业基准、竞品或宏观事件作为参照
- 其他 data- 技能在分析过程中遇到“缺背景”的情况

## 前置条件
- 可检索的来源：工作区文档（md/docx/pdf/pptx/xlsx）、代码仓库与变更记录、`data-context/` 语义层、用户提供的链接；公开信息可用 `web_search`/`web_fetch`
- 若用户启用了其他连接器插件（如文档、日历、IM 类），可引导使用；本技能不假设其存在
- 来源可信度与笔记格式见 `references/source-notes.md`

## 分步流程
1. **明确检索目标**：写下要回答的具体问题（如“5 月 3 日前后是否有影响下单的变更？”），以及需要的上下文类型：定义 / 目标 / 事件 / 基准 / 先前结论。
2. **确定锚点**：列出检索关键词——指标名及同义词、产品/功能名、时间段、团队名、项目代号。
3. **本地优先**：
   - `file_read data-context/README.md`、`metrics.md`（如存在）
   - `file_grep` 在工作区搜锚点（`*.md`、`*.sql`、`*.yml`、`*.ipynb`）
   - `doc_read` 读取命中的 docx/pdf/pptx/xlsx
   - `shell_run` `git log --since=... --until=... --oneline -- <路径>` 查代码/埋点/配置变更时间
4. **外部补充**（仅当需要公开信息，且不涉及敏感数据）：`web_search` 找行业报告、官方统计、公告；`web_fetch` 读取原文。优先一手来源（官方统计、公司财报、监管文件），二手来源需标注。
5. **追到权威来源**：从聊天/摘要等“发现渠道”出发，追溯到最终来源（正式文档、代码、原始公告），记录链接或路径。
6. **只提取与决策相关的内容**：每条上下文说明“它如何影响本次分析的解读”。
7. **显式处理冲突**：同一事实多个来源不一致时并列，给出倾向与理由，必要时 `ask_user`。
8. **适可而止**：当上下文已足以确定分析框架时停止检索，不追求穷尽。
9. **输出上下文笔记**：写 `analysis/context-notes.md`（格式见下），供后续技能引用。

## 工具与参数要点

- `file_glob`/`file_grep`：在工作区里检索关键词、指标名和项目代号。`doc_read`：读取 docx/pdf/pptx/xlsx 资料
- `web_search`/`web_fetch`：查公开的行业、竞品和宏观信息。每条都要记录 URL 和访问日期
- `browser_automation`：处理需要渲染或登录的内部页面。只用用户已登录的会话，不输入密码
- `agent_run`：来源很多时按来源类型分给子任务并行检索，由主流程合并去重
- `file_write`：把笔记写到 `data-context/business-notes.md`，或按 `references/source-notes.md` 的格式输出
- `ask_user`：来源冲突或缺少关键信息时再提问，不凭空补全

## 质量检查
- 每条事实都有来源（路径、链接、提交号、文档名+日期），并标注可信度（高/中/低）
- 日期精确到天，注明时区（若相关）
- 区分“文档里写的”与“推断的”
- 不把内部敏感信息写进对外报告；不把内部数据粘贴到外部搜索

## 失败回退
- 本地没有文档：说明搜索过的位置，用 `ask_user` 请用户提供背景或确认关键事件
- 网络不可用或被拒：只用本地信息，标注外部基准缺失
- 来源互相矛盾且无法裁决：列入“待确认”，并在分析中对两种情形分别说明影响

## 交付格式
`analysis/context-notes.md`：
```markdown
# 业务上下文笔记：<主题>（检索于 YYYY-MM-DD）
## 检索目标
## 关键上下文
| # | 事实 | 日期 | 来源 | 可信度 | 对分析的影响 |
## 指标定义与目标
## 冲突与待确认
## 未找到的信息
```
对话中用 3–5 行概括最关键的上下文。

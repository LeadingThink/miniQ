# 严重度、置信度与问题卡片

## 严重度（看对下游用途的影响，而不是问题本身看起来多大）
| 级别 | 判定 | 例子 |
|---|---|---|
| 高 | 会导致关键指标或决策明显错误；影响计费、合规、对外披露；无法用简单说明绕过 | 主键重复导致收入重复计算 8%；最近 3 天数据缺失却进入周报 |
| 中 | 影响部分分群或次要指标；可以通过过滤/说明暂时规避 | 某渠道 12% 记录缺少地区；测试账号混入但占比 0.3% |
| 低 | 外观/规范问题，或影响可忽略 | 字段命名不一致；少量前后空格 |

## 置信度
- 高：有直接证据（计数、样例、对账差额），原因已确认
- 中：现象确定，原因是推测但有旁证
- 低：只有间接迹象，需要进一步验证

## 问题卡片模板
```
### [高] 订单表存在重复加载
- 现象：2024-05-03 的订单行数为前后 7 日均值的 2.02 倍
- 证据：order_id 重复 18,432 条（占当日 49.6%）；样例 ID：A1001、A1002…
- 影响：5 月 GMV 虚高约 4.1%；所有基于订单数的转化率偏高
- 可能原因：5/3 调度任务重跑未去重（置信度：中，依据：任务日志有两次成功记录）
- 建议：按 (order_id, updated_at) 去重；新增 unique(order_id) 规则每日运行
```

## 报告结构
1. 结论：可用 / 有条件可用（列出条件） / 不可用
2. 数据集与粒度、检查范围与时间窗
3. 检查执行情况表：检查项 | 结果 | 失败数 | 失败率
4. 问题卡片（按严重度、再按影响排序）
5. 时间与分群异常图（行数/缺失率时间序列）
6. 建议的自动化规则与负责人
7. 假设、局限、待确认问题

## 何时建议固化为自动检测
- 规则稳定（不会每周变化）、失败后果重要、维护成本低
- 优先：主键唯一、关键字段非空、新鲜度、行数波动、金额对账
- 暂缓：依赖大量人工判断的业务合理性检查
